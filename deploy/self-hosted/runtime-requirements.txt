# Hash-pinned install set for clawmetry's OWN runtime dependencies in the
# SIGNED self-hosted release image (Dockerfile.release in this directory).
#
# Direct requirements: clawmetry's install_requires, with the markers
# evaluated for this image's interpreter (python:3.14-slim) --
# flask>=2.0,<4 waitress>=2.0 cryptography>=50.0.0 cffi>=2
# duckdb>=0.10,!=1.4.5 websocket-client>=1.6 truststore>=0.8
# certifi>=2024.7.4
#
# `pip install "$1[otel]"` is what this file stands in front of. That line
# installs the published wheel, and otel-requirements.txt already satisfies the
# two names the `[otel]` extra adds -- but the wheel's own eight requirements
# had nothing in front of them and resolved live against the index at build
# time. Those are open floors: `flask>=2.0,<4` spans two major versions,
# `certifi>=2024.7.4` and `duckdb>=0.10` span years of releases. Two builds of
# the SAME clawmetry version, a week apart, could bake different flask,
# cryptography and duckdb bytes into the image an org then runs.
#
# This is the third and last unpinned resolve in this file, and it was the
# largest: 15 packages against otel-requirements.txt's 2. The FROM line is
# pinned by digest and the OTLP layer is hash-pinned; the layer between them
# gave both of those back.
#
# This matters more here than in the root Dockerfile, which got the same
# treatment first (.github/requirements/docker-runtime.txt). This image is
# PUBLISHED and SIGNED: container-image.yml pushes it to
# ghcr.io/vivekchand/clawmetry, cosign signs the index and every platform
# manifest, and an SPDX SBOM is attested to each platform digest. An SBOM and
# a signature attest to bytes. If two builds of one clawmetry version can bake
# different flask bytes, the signature still verifies and the SBOM still
# validates -- they just describe whatever the builder happened to resolve that
# morning. Pinning is what makes the attestation mean "this clawmetry release",
# and not "a clawmetry release plus that day's index".
#
# Deliberately a SEPARATE file rather than hashes added to requirements.txt or
# to the root image's docker-runtime.txt:
#   - requirements.txt is the manifest a pip user installs from and setup.py
#     derives from; --hash lines there would force every `pip install -r
#     requirements.txt` on any interpreter to match hashes resolved for 3.14.
#   - docker-runtime.txt pins the whole of requirements.txt, which carries the
#     dev/test set (pytest, playwright, requests). None of that belongs in a
#     published server image. This file pins setup.py's install_requires
#     instead, which is what the WHEEL declares -- a different closure, hence
#     a different file. Where the two overlap they agree exactly today, and
#     tests/test_selfhosted_runtime_pin.py is what keeps this one honest
#     against setup.py.
#
# zstandard is absent on purpose: install_requires carries it only for
# `python_version < "3.14"`, and this image is 3.14, so the wheel does not ask
# for it here.
#
# Installed with `pip install --require-hashes`, which refuses to install
# anything not listed here with a matching hash -- so the image gets the exact
# artifacts this file names, or the build fails. Every transitive dependency is
# present because --require-hashes demands the whole closure; that is why an
# 8-name manifest expands to the 15 below (pycparser arrives under cffi;
# blinker, click, itsdangerous, jinja2, markupsafe and werkzeug under flask).
#
# Each version lists the sha256 of EVERY distribution PyPI publishes for it
# (wheels for each platform, plus the sdist). pip accepts a download whose
# hash is any one of them, and the image is built for linux/amd64 AND
# linux/arm64 from one file, so both architectures' wheels have to be here.
#
# Regenerate with `python3 scripts/resolve_selfhosted_runtime_pins.py --write`,
# which resolves the closure with the markers evaluated for 3.14 and refuses to
# write a set that is not installable on both architectures. Dependabot owns
# the routine bumps (.github/dependabot.yml watches this directory for pip) and
# rewrites the hashes along with the versions.
