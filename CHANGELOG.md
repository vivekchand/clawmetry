### Fixed: a published release could go to PyPI and never deploy, silently (2026-09-08)
- **Why:** found while shipping #5645/#5651 and watching the chain end to end. `auto-deploy-cloud.yml` decides what to pin by reading PyPI's `info.version` — correct, because `dashboard.py`'s `__version__` is permanently one or more releases stale (release-on-merge publishes the bump without committing it back). But its **push trigger** fires on the `[RELEASE]` merge commit, which touches `CHANGELOG.md` — and that push happens *before* `release-on-merge.yml` uploads. So auto-deploy started, read PyPI's latest (still the PREVIOUS release), pinned that, and its own "wait for version on PyPI" step passed instantly because the version it was waiting for was the old one already there. Nothing re-triggered it afterwards. Measured on 0.12.829: the merge fired auto-deploy at 23:27:51, which logged `Latest published OSS version: 0.12.828` and pinned it; 0.12.829 published seconds later and had to be dispatched by hand. The failure mode is the dangerous one — **silent and total**: PR merged, wheel on PyPI, CHANGELOG updated, release job green, and the hosted dashboard serving the previous bundle indefinitely. Every artifact a person would check reports success, which is exactly why "verify the SERVED artifact" is the only honest done-check.
- **What:** `release-on-merge.yml` now dispatches `auto-deploy-cloud.yml` explicitly **after the upload** — the only ordering in which "PyPI's latest" is the release that job just produced. It sits with the two dispatches that already exist there for the same reason: GITHUB_TOKEN activity does not cascade into new workflow runs, so a push trigger cannot be relied on (that rule already cost v0.12.658 its `.dmg` and 0.12.757 its canary). Non-blocking like the others — the wheel is published by then and a failed dispatch must not fail a completed release. The early push-triggered run is left alone and is harmless: auto-deploy's no-downgrade guard makes an already-stale target a no-op. That guard's comment claimed the job "reads `__version__` at the TRIGGERING commit", which stopped being true when the source moved to PyPI; it now describes both real reasons the target can be behind, including this one.
- **Verified:** 7 new guards in `tests/test_release_dispatches_cloud_deploy.py` — that the dispatch exists, that it is **after** the upload (ordering is the entire fix), that it stays non-blocking, that it targets a branch rather than the new tag, that the job keeps `actions: write` (without it every dispatch silently 403s), and that auto-deploy keeps reading PyPI rather than the stale checkout and keeps polling what *pip* reads rather than the JSON API. 4 of the 7 proven red against `origin/main`; the other 3 assert preserved behaviour and are correctly green on both. Both this file and `tests/test_release_canary_reachable.py` are now named in `ci.yml` — the canary guard was referenced only in a comment and ran in **no job at all**, which is the same "a guard added without a line here runs nowhere" trap `ci.yml` warns about in its own text.

### Fixed: the hosted Sessions tab was empty for every runtime but the busiest one (2026-09-08)
- **Why:** one founder screenshot of app.clawmetry.com. The header read "Codex, 15 sessions" and the panel directly beneath it read "No Codex sessions have a transcript yet", while the same machine's localhost dashboard listed them fine. Two lanes feed those two numbers: the count comes from the uncapped session-metadata push to `/ingest/sessions`, which carries every session of every runtime, and the list comes from the encrypted snapshot's `transcripts` map, which `sync._build_transcripts` filled with the 8 most recently active sessions node-wide and no per-runtime fairness at all. That machine has 1866 claude_code sessions against 16 codex ones, so claude_code took all 8 slots on every cycle and no Codex transcript had ever reached the cloud. Run against the live daemon, the payload was 8 claude_code transcripts and nothing else. - **What:** a second selection pass reserves slots per runtime. `LocalStore.query_recent_sessions_by_runtime` is one window function partitioned by runtime over the events table, so the newest N sessions of a quiet runtime are found without scanning past a loud one; sessions with no renderable turn are excluded so a reserved slot is never spent on a row the UI drops. The reserved slots carry a shorter message cap than the global ones (12 against 80): measured on a machine carrying every family adapter that is plus 121 KB raw and plus 27 KB gzipped, against plus 427 KB raw at a cap of 24, and the replay pages older messages on demand through `_oldest_contiguous_ts`. `CLAWMETRY_SNAPSHOT_PER_RUNTIME_SESSIONS=0` restores the old behaviour and a failing store read degrades to it on its own. The freshness cache was resized to cover every slot, or a many-runtime box would rebuild all of them every cycle. Second half of the same bug: the runtime-scoped empty state no longer contradicts the header. When the header counts sessions it now says how many the machine has and why none are readable here yet, with a singular form, instead of asserting that none exist.
- **Verified:** decrypted the live cloud snapshot after the change: 35 transcripts covering every runtime with activity on that machine, including two real Codex sessions with titles, where before it was 8 claude_code and nothing else. 12 guards in `tests/test_snapshot_transcripts_runtime_fair.py`, named explicitly in `ci.yml`, with 4 proven red against a checkout of the unfixed `sync.py`. The new query costs 0.13 s on a 900 MB store, and the whole build stays at 0.69 s cold and 0.26 s warm.
### Fixed: the home screen's Active Tasks panel told four lies on one screen (2026-09-08)

Status classification moves into one `_ovBucketOf()` that the card renderer and the grouping both read (they derived it independently before, which is exactly how they came to disagree), with `failed`/`error`/`aborted` a first-class bucket alongside the preserved legacy heuristic. End-time derivation moves into one `_ovEndedMs()` that is allowed to answer *unknown*: `updatedAt` counts only once the record shows the spawn actually ran, so a never-ran spawn returns 0, renders no timestamp, and does not enter the "recent" window at all. The empty state now names the runtime ("No active tasks for Codex") and says how many tasks are on other runtimes, instead of claiming "The AI is idle" while another runtime is flat out. Also deleted: `loadActiveTasks()` / `startActiveTasksRefresh()` / `humanTime()` / `humanTimeDone()` and the hidden `#active-tasks-grid` div that existed only so that dead renderer would not throw — it was never called, had drifted away from the live one, and filtered runtimes through the resolver bug above, so it would have blanked the panel had anyone wired it up. ### Fixed: a Windows pip "success" that silently installed a 664-release-old ClawMetry (2026-09-08)
- **Why:** #5639, found while chasing #5628. Wheels-only pip (`--only-binary=:all:`, which every Windows install path uses) does not merely turn a missing wheel into an honest error — with a bare `clawmetry` requirement it can avoid the error entirely by backtracking **clawmetry itself** until the graph resolves. Measured against live PyPI on py3.11: a `win32` interpreter resolves clawmetry **0.12.163**, from before duckdb was a dependency at all; `win-arm64` resolves 0.12.793, backtracked past the `cryptography>=50` bump; only `win_amd64` gets the current release. Nothing errors — the dist-info is complete, the entry point exists, the splash clears — so the user runs a 2026-06-era ClawMetry against a current cloud, the 60s upgrade cadence re-resolves to the same old version forever, and no field-failure report is ever sent, because from the shell's side the install succeeded. Strictly worse than the failure it replaced, and invisible to the telemetry that exists.
- **What:** every pip install the shell runs now carries a floor — `clawmetry>=<bundle version>`, from the version stamped into the bundle at build time. The bundle's own version is the floor because the shell was BUILT at that release, so PyPI demonstrably has it; `>=` and not `==` on purpose, so pip may still backtrack for a legitimate reason (an index-propagation race in the minutes after a release — this repo ships several a day) but never past the shell's own age. The floor cannot heal machines already stranded, because a backtracked install is COMPLETE and the warm-launch short-circuit accepts it, so `_is_stranded_on_an_old_version` stops trusting a venv whose clawmetry is older than the shell booting it and falls through to the (now floored) install path. That check is latched on disk to one attempt per stranded version: the heal reruns pip on the boot path and, on Windows, a floored failure now provisions an interpreter, so a check that fired every launch would mean a pip run and possibly a winget install on every launch of a machine it cannot fix — after one attempt the launch proceeds on the old install, because a ClawMetry that is behind still beats a shell that will not open. The CLI installers have no bundle stamp to floor against, so they verify the result functionally instead: after pip reports success they `import clawmetry, duckdb, cryptography` and fail with actionable guidance if it is missing, since a release old enough to have been backtracked to does not carry today's dependency set. A pre-install `clawmetry>=<latest>` pin was rejected there — with nothing above latest it acts as `==`, which would also block pip's legitimate backtracking and turn a propagation race into a hard failure.
- **Verified:** 10 new guards in `tests/test_desktop_bootstrap_resilience.py`, 9 proven red against a checkout of the unfixed files (the tenth asserts preserved behaviour — a current install must still short-circuit — and is correctly green on both). 62 pass in that file; 353 pass across the desktop and installer suites. `install.ps1` is executed for real by `install-test.yml` on a `windows-latest` runner with Python 3.12, which exercises the new PowerShell rather than only reading it; `install-clawmetry.ps1` is not covered by that workflow's path trigger and is checked by content assertion only. The three resolutions above were re-measured against live PyPI (`pip download --only-binary=:all: --python-version 3.11 --implementation cp --platform <tag>`), not inferred from wheel listings.

### Fixed: a blocked pip index told a Python 3.11 user their Python was too old (2026-09-07)
- **Why:** the field-failure pipeline filed its first issue, #5628 — `no_distribution` on Windows, bootstrap Python **3.11**, one install, one event — and the hint that machine had been shown was "Python too old or PyPI unreachable — install python.org Python 3.11+ and relaunch." That advice cannot ever be right: `_bootstrap_python()` enforces the 3.9 floor before a venv is created, so pip only runs on an interpreter that already passed it, and this user was being sent to reinstall the version they already had. Worse, the class was collecting failures that were not about the interpreter at all. Captured from pip 26.1.2: an index on a refused port and an index behind a self-signed certificate BOTH end in `ERROR: No matching distribution found for clawmetry`, and that branch ran before the TLS and network branches — so a blocked corporate proxy, a captive portal and an intercepted TLS handshake all rendered as "Python too old", while the two hints that name a proxy sat unused.
- **What:** `_classify_pip_failure` now reads pip's own candidate list to tell an index it could not READ from an interpreter PyPI has no wheels for. `(from versions: none)` means the index yielded no candidates at all, so paired with TLS evidence the class is `tls_intercepted` and with transport evidence it is `network`; a real version list means the index answered and nothing in it fits, which is the only true `no_distribution` — now worded for its two remaining causes (a private mirror that does not proxy PyPI, or an interpreter without wheel coverage) and no longer blaming the version. The closed enum is unchanged, deliberately: a new code would be coerced to `unknown` by the cloud sink's `_FAILURE_CLASSES` whitelist and the next report would be less legible, not more. The probe additionally records the interpreter's `sysconfig.get_platform()` in `runtime/bootstrap-python.json` and logs it next to the version, because "3.11" alone cannot say which interpreter pip resolved wheels for (win32 has no duckdb wheel at any Python version); it is a `bootstrap.log` line, not a payload field, so nothing new leaves the machine.
- **Verified:** the four snippets in `tests/test_desktop_bootstrap_resilience.py` are pip's real output, captured by pointing pip at a refused port, a 404 index and a self-signed index; the fourth is a genuine incompatible-candidate list. Six new guards, all six proven RED against a checkout of the unfixed `desktop/app.py` (43 passed after, 6 failed before), in a file `ci.yml` names explicitly. Also checked what the two falsified theories actually do, by resolving clawmetry's dependency graph against each Windows tag on live PyPI: `win32` and `win-arm64` do NOT produce `no_distribution` on py3.11 — they resolve, by backtracking clawmetry itself to 0.12.163 and 0.12.793 respectively. That silent downgrade is a separate defect, filed rather than folded in here.

### Changed: when PyPI has nothing this Python can install, the shell installs a Python that works (2026-09-07)
- **Why:** the fix above stops the shell mis-blaming the interpreter, which leaves the honest cases — an interpreter PyPI genuinely has no artifact for — still ending in "install python.org Python X and relaunch." Python is a dependency ClawMetry installs, not a prerequisite it asks for: that is already how a machine with NO Python is handled (the NSIS `-PythonRuntime` section, then `winget install Python.Python.3.12`), and a machine whose Python has no usable wheels is the same problem one step later. Asking is also the *slower* path for the person: they have to pick a version, and the obvious pick is wrong.
- **What:** `_retry_on_known_good_python` — on Windows, a pip failure classified `no_distribution` or `compiler_demand` now provisions the pinned interpreter (`winget install Python.Python.3.12`), rebuilds the venv on it and retries pip once, before any hint is shown. The pinned interpreter is deliberately **not the latest Python**: wheel coverage lags a release by months, and the newest interpreter is the one most likely to have none — the 2026-08-29 failure was python.org 3.14 with no cffi cp314 wheel. It is addressed by path (`%LOCALAPPDATA%\Programs\Python\Python312\python.exe`), never by re-probing, because `_bootstrap_python` tries `py` first and the `py` launcher resolves to the *newest* installed interpreter — which is precisely the one that just failed. The pin lives in one place (`KNOWN_GOOD_PYTHON_MINOR` / `_WINGET_ID` / `_DIRNAME`) so the winget id and the install directory cannot drift apart, and the remaining last-resort hints now name that same minor instead of a range that invites the newest. No install is attempted for `network`, `tls_intercepted` or `permissions` — a new interpreter cannot fix a proxy, and downloading ~30 MB to fail identically reads as broken software. That guard only works because the classifier fix above landed first: a refused index used to *be* `no_distribution`.
- **Verified:** 8 further guards, red against the unfixed file (15 of 15 new guards red in total; 52 passed after). They pin the retry using the pinned path rather than a re-probe, at most one attempt, no attempt when already on the pinned minor, no attempt for network/TLS/permissions failures, the original failure and its accurate hint surviving a machine where winget is blocked, and the pin's three constants agreeing with each other. Writing them found a real fragility: `_retry_on_known_good_python` read `bootstrap_python_version`, which `bootstrap()` assigns on entry rather than in `__init__`, so the method raised `AttributeError` on a supervisor built via `__new__`.

Both numbers were right; they measure different events. `claude_code_session_map` recorded `startedAt` - the moment claude_code *wrote its session record* - and the pid-reuse guard compares its recorded value against the *process's* start time from `ps -o lstart=`. On the machine where this was found the two are 7 seconds apart, so the guard refused every pause, stop and kill on every session, having correctly detected a mismatch between a process start and something that was never a process start. The preference was deliberate and the comment explains it: `procStart` is a ctime string claude_code renders in UTC, which does not compare textually against local-time `ps` output, so `startedAt` looked like the unambiguous choice. But that comparison problem was already solved - `_start_tokens_equivalent` normalises both sides to an instant and reports `verified_tz_normalized` - while measuring the wrong event had no remedy anywhere downstream.
- **What:** the map records `procStart`, the process's own start time, and exposes `startedAt` separately as `started_at` for callers that want to know when the session began. Where no usable `procStart` exists the recorded start is `None`, so `verify_pid` degrades to an honest liveness check; falling back to `startedAt` would restore a value guaranteed to mismatch, which refuses every action.
- **Verified:** the test that asserted the old preference is replaced by one asserting the corrected contract, plus an end-to-end test that spawns a real process, renders its start the way claude_code does (a UTC ctime string), and requires the guard to pass; both are red against the unfixed file. Against the founder's live node, the guard went from refusing every session to passing 10 of 11 - the eleventh has no session record at all and is correctly refused.

### Fixed: Guard lists a running session in milliseconds instead of minutes (2026-09-05)
- **Why:** a founder started a Claude Code session at 02:36:32, watched the Guard tab for over a minute, and it never appeared — the tab whose stated job is "what is running right now, and the button to stop it". Guard read its running-session list purely from DuckDB, so its freshness was the sync daemon's entire cycle: measured on that node, `sync` passes took 60-78s normally, and one took **288 seconds** immediately after `runtime_backfill` raised the claude_code ingest depth from 50 to 1088 sessions. The new session was born 2m18s into that blind window, so no amount of clicking Refresh could have produced it. The same staleness was also hiding sessions that had been running for hours: on that node a live probe found **22 running Claude Code processes while Guard listed 11**, so 12 live agents had no Kill button at all, and one listed row pointed at a process that had already exited. `POLL_INTERVAL = 15` in `sync.py` describes an intent the cycle has not met in a long time, and coupling the kill switch to it means the one surface that must be real-time is the one furthest behind.
- **What:** `process_control.live_sessions()` reports every session this node can see as a **running process**, read from the per-pid records the runtime writes itself (`~/.claude/sessions/<pid>.json`) off the memoized map #5529 added — 22 sessions in 8ms, with dead pids filtered so a stale record never renders a Kill button attached to nothing. `/api/guard/sessions` merges those into the store rows via `_live_only_rows`, matching on `native_session_id` because store ids carry the `<runtime>:` namespace and the probe reports what the runtime wrote — comparing raw strings would have listed every session twice. A merged row is namespaced like a store row so the id posted back to `/api/guard/control` is identical whichever source it came from, carries the runtime's own session name as its title rather than a bare uuid, and is stamped `pending_ingest` so the Cost column renders "—" instead of a `$0.00` that would read as measured. Sorting gains recency as its **last** key: money still decides the top of the table, so a just-started session rises to the top of the unflagged group without ever burying a $170 loop. Coverage is stated, not implied — only runtimes in `LIVE_PROBE_RUNTIMES` are listed, because a cwd+argv runtime can be checked but not enumerated without a full process walk, and a probe that silently covered one runtime while implying it covered all of them would be worse than one that says which it covers. A probe that throws costs the extra rows, never the tab.
- **Free-tier follow-up (same PR):** de-duplication was first keyed on the store row's runtime label, which `_session_runtime` resolves through `waste_flags.runtime_from_session_id` — a function that returns `"openclaw"` for every id unless clawmetry-pro is installed. On a Free install the key therefore never matched and the probe listed **every Claude Code session twice**. It passed on a Pro laptop and was caught only by CI, which runs OSS-only. Matching is now against the store's raw ids in both the bare and namespaced spellings and never asks a row what runtime it is.
- **Verified:** 9 tests in `tests/test_guard_live_probe.py`, 7 of which were proven red against unfixed `origin/main` (the eighth is the no-duplicates guard, which passes trivially when there is no probe at all). End to end against this machine's real processes: `live_sessions()` returned 22 live sessions in 8.0ms, and `/api/guard/sessions` went from 11 rows to **23** (12 from the probe) in 94ms with **0 duplicate ids** and flagged sessions still ranked on top. `tests/test_guard_live_probe.py` joins the moat-tests CI job and `make test-moat` alongside the guard tests; the existing 90 guard + process-control tests still pass.

### Release: the Cost tab stops starving every other tab (#5524) (2026-09-05)
- **Why:** on a founder node the Cost page sat on "Loading..." and, once it had, every other tab failed with it — Brain "Failed to load: timeout", Agents blank, and Sessions reporting "No Claude Code sessions have a transcript yet" beneath its own header counting 61. Each Cost roll-up is a separate endpoint the browser fires at once, and each independently pulled the newest 20k-50k events: 21 scans per page load, 37.7 MB per scan across the daemon RPC, of which the SQL is 0.9 s and the rest is decode plus serialise plus parse. That saturates the daemon's single DuckDB connection until sibling reads exceed `_PROXY_TIMEOUTS` and their handlers return `None`, which the tabs render as EMPTY. Nodes auto-update, so publishing is what makes the fix real.
- **What:** this release carries #5524. `LocalStore.query_events_slim()` returns the same rows, filters and order minus the two payload keys that carry the bulk (`content` 66.5%, `tool_calls` 28.5% of decoded bytes) and that no roll-up reads; a denylist, so any other key keeps its numbers exactly. The RPC for that shape is memoised and single-flighted so concurrent endpoints share one round trip, and `_scan_events_slim` falls back to the full shape when a not-yet-restarted daemon does not know the new one. Dashboard and daemon side, so the cloud pin follows.
- **Verified:** #5524 shipped 9 tests, all 9 proven red against the unpatched tree, covering the denylist boundary, single-flight (8 concurrent callers, 1 round trip), the never-cache-the-unavailable-sentinel rule and the upgrade-skew fallback. On the founder node the Cost page's own heavy scans went 21 to 2 per request, and plugin / skill / model / runtime roll-ups computed from slim rows are byte-identical to the same roll-ups over full rows on the live 46k-row store. 40 checks green on #5524, drift-bot clean.

### Fixed: Pause, Stop and Kill did nothing on every runtime except OpenClaw (2026-09-05)
- **Why:** clicking Pause in the Guard tab returned `Pause did not succeed: session_not_in_claude_map` on a founder laptop running 0.12.812, for all five flagged Claude Code sessions. The store namespaces every family-runtime session as `<runtime>:<native id>` (`sync.sync_family_runtimes` stamps `ns_id = f"{runtime}:{s.id}"`), `GET /api/guard/sessions` returns that id, the UI posts it back to `/api/guard/control`, and `process_control.resolve_session` handed it unchanged to `resolve_claude_code`, whose map is keyed on the bare uuid Claude Code writes into `~/.claude/sessions/<pid>.json`. Every lookup missed. The button was not the whole blast radius: the daemon's autonomous path (`sync._emit_detector_incidents` -> `_guard_actuate`) feeds the same store id through the same resolver, so a Guard policy could never actuate on a family runtime either. OpenClaw was unaffected only because its ids are bare and its stop/kill go through gateway task cancel. The kill switch, the product's one intervention surface, was inert for 26 of the 27 runtimes it claims to control.
- **What:** `process_control.native_session_id(runtime, session_id)` strips an exact `<runtime>:` head, once, at the only boundary where a store id becomes a process lookup (`resolve_session`), so every resolver - claude_code, copilot, qwen_code, cursor, and the cwd+argv family - sees the native id the runtime itself wrote. Only that runtime's own head is removed and only the first one, so a native id containing a colon keeps every character after it and a mismatched prefix is never silently truncated. Second fix in the same surface: `runtime_control_support` answered `controllable: True` for every `claude_code` session without asking the resolver (unlike the `cursor` branch), which is why four live-looking buttons were rendered for sessions whose only possible outcome was an alert box; it now resolves the session and refuses a missing record or an exited pid with a sentence an operator can act on. Because the Guard list asks for that verdict once per row, `claude_code_session_map` gains a memo keyed on the sessions directory and its mtime (2 s TTL as a backstop), so a 50-row list scans the directory once instead of fifty times and a session that starts or ends still shows up immediately. Third: `tests/test_process_control.py`, `tests/test_process_control_windows.py` and `tests/test_guard_control_capability.py` ran in no CI job at all - the product's one intervention surface had zero coverage on every PR, which is how a resolver that could not resolve anything shipped. All three join the moat-tests job and `make test-moat`.
- **Verified:** 5 new tests in `tests/test_guard_control_capability.py`, all proven red against the unfixed file: a prefixed id resolving to its pid, `native_session_id` leaving a foreign prefix and an inner colon alone, the refusal for an unresolvable session and for a dead pid, and the memo invalidating when a session appears. End to end against a real process on macOS through `sync._guard_actuate` with the exact id the Guard tab posts (`claude_code:<uuid>`): pause moved it to state `T`, resume back to `S`, kill ended it - and the same script against unfixed `origin/main` fails with the user's exact `session_not_in_claude_map`. Against the founder's live node, all six sessions in `GET /api/guard/sessions` resolve to live pids (47022, 9088, 9912, 57661, 85799, 50051) where every one of them missed before.
### Perf: session phase and session context rows are written only when they change (#5528) (2026-09-05)
- **Why:** after #5496, #5498 and #5500 the one table on a real node still carrying many dead versions per live row was `session_phase` (12 per row eleven minutes after a compaction): the daemon records every session's phase on every tick, and an upsert that changes nothing is still a DELETE plus INSERT on a keyed table. `session_context` had the same shape at two versions per row, because the family ingest re-delivers every context row each time it re-reads a session.
- **What:** `record_session_phase` hashes the content columns (runtime, phase, status, basis, end reason, resolvable, cwd) and skips the write when the stored row has the same hash and was observed within `CLAWMETRY_PHASE_REFRESH_SECS` (600), so `observed_at` never goes stale for more than that; a phase or directory change still writes and still moves `phase_since` exactly as before. `ingest_session_context` looks up what the table already holds for the batch's sessions once and skips a row whose stored first/last timestamps already cover it and that brings no summary the row lacks; a later occurrence still bumps `turns`. Both honour `CLAWMETRY_UPSERT_DEDUPE=0`.
- **Verified:** 7 tests in `tests/test_store_phase_context_dedupe.py` (same phase on the next tick writes nothing; a changed phase or cwd writes and moves the stamp; the freshness floor refreshes `observed_at`; dedupe survives a restart; context re-delivery writes nothing; a later occurrence bumps turns and a first summary is kept; kill switch). 4 of them fail on the unpatched store. The phase-model, context-ingest, context-route and query-contract suites pass unchanged (75 tests). Wired into the CI MOAT file list.
