### Fixed: a killed agent said "Running", and Pause/Stop/Kill were a black box (2026-09-05)
- **Why:** two field reports about one column of the Guard tab. First, after a successful Stop or Kill the row still read `Running` in the Status column and `Not controllable` in the Control column: the tab contradicting itself, and neither half answering the operator's real next question, which is how to get back into that conversation. Both halves had one cause — `runtime_control_support` returned `controllable: False` for two completely different facts, "the process is gone" and "this runtime can never be signalled", separated only by prose, so the UI printed one label for a session the operator had just killed and for a Grok Bot agent that runs on xAI's cloud VM and never had a local process. Second, the whole Pause/Stop/Kill interaction was one browser `confirm("Kill this agent?")` and one `alert()` carrying a single token. An operator could not see which pid was about to be signalled, that Kill takes the entire process tree (six processes on a typical Claude Code session, MCP servers and `caffeinate` included), whether the pid-reuse guard had agreed it was still the right process, or afterwards which step had refused. The most dangerous control in the product was the least legible one.
- **What:** `process_control.runtime_control_support` now answers a machine-readable `state` — `controllable` / `exited` / `unsupported` / `unknown` — and every caller branches on that rather than on the prose reason. Claude Code writes one per-pid session record per *running* process and removes it on exit (verified on the reporting node: 28 records, 28 live pids, zero stale), so its absence is evidence the process ended; an unrecognised resolver code defaults to `unknown`, never `exited`, because a Stopped pill on a session still burning money would be worse than the bug being fixed. New `clawmetry/resume_hints.py` answers, for every shipped runtime, either a real command line or an honest statement that none exists: each command was read off the real binary's `--help` or upstream's own docs and carries that `source`, hosted runtimes get words rather than an invented flag, and the command carries the *native* session id, not the store's `<runtime>:<id>` spelling — the same boundary that once made every intervention miss. `process_control.control_preflight` performs the read-only half of the guarded path (resolve, verify, walk the tree) and **sends nothing**, returning the pid, argv, working directory, the whole process tree, the pid-reuse guard's verdict and the ordered signal plan for that action on that OS; `guard_actuator.guard_actuate` takes an optional `trace` list and appends each step as it happens, so a partial record survives a failure and a policy's automatic kill records what a human's does. `graceful_kill` now reports the tree it snapshotted, whether it escalated to SIGKILL and which pids it killed — it already knew, nobody was told. The tab renders a Stopped pill, the resume command with one click to copy it, and a native `<dialog>` carrying the plan before and the trace after. The dialog is native because the app root carries a transform for the zoom control, which makes it the containing block for `position: fixed`, so a fixed overlay there covers the scrolled document instead of the viewport and drifts off screen.
- **Verified:** 95 tests across `tests/test_guard_resume_hints.py`, `tests/test_guard_resume_route.py` and `tests/test_guard_control_transparency.py`, every one proven red against the unfixed tree first, including a test that pins every shipped runtime to a resume answer so adding a runtime without one fails CI. One trap worth naming: `routes.guard._detail_safe` is a CodeQL-credited sanitiser whose allowlist silently drops what it does not recognise, and every one of these strings passes through it — an em dash welded two clauses into "the main pid only the same thing as pressing Ctrl-C", and `runtime=claude_code` reached the browser as `runtimeclaude_code`. The copy is now written inside that alphabet and a test pins it there, rather than widening a security sanitiser to suit prose. ### Fixed: the pid-reuse guard refused every Guard action because it compared the wrong timestamp (2026-09-05)
- **Why:** with the session-id namespace fixed (#5529), Pause on a real Claude Code session stopped answering "session not found" and started answering `pid_guard_refused:start_mismatch(recorded=epoch:1788471021, live=lstart:Thu Sep 3 23:30:14 2026)`. Both numbers were right; they measure different events. `claude_code_session_map` recorded `startedAt` - the moment claude_code *wrote its session record* - and the pid-reuse guard compares its recorded value against the *process's* start time from `ps -o lstart=`. On the machine where this was found the two are 7 seconds apart, so the guard refused every pause, stop and kill on every session, having correctly detected a mismatch between a process start and something that was never a process start. The preference was deliberate and the comment explains it: `procStart` is a ctime string claude_code renders in UTC, which does not compare textually against local-time `ps` output, so `startedAt` looked like the unambiguous choice. But that comparison problem was already solved - `_start_tokens_equivalent` normalises both sides to an instant and reports `verified_tz_normalized` - while measuring the wrong event had no remedy anywhere downstream.
- **What:** the map records `procStart`, the process's own start time, and exposes `startedAt` separately as `started_at` for callers that want to know when the session began. Where no usable `procStart` exists the recorded start is `None`, so `verify_pid` degrades to an honest liveness check; falling back to `startedAt` would restore a value guaranteed to mismatch, which refuses every action.
- **Verified:** the test that asserted the old preference is replaced by one asserting the corrected contract, plus an end-to-end test that spawns a real process, renders its start the way claude_code does (a UTC ctime string), and requires the guard to pass; both are red against the unfixed file. Against the founder's live node, the guard went from refusing every session to passing 10 of 11 - the eleventh has no session record at all and is correctly refused.

### Fixed: Guard lists a running session in milliseconds instead of minutes (2026-09-05)
- **Why:** a founder started a Claude Code session at 02:36:32, watched the Guard tab for over a minute, and it never appeared — the tab whose stated job is "what is running right now, and the button to stop it". Guard read its running-session list purely from DuckDB, so its freshness was the sync daemon's entire cycle: measured on that node, `sync` passes took 60-78s normally, and one took **288 seconds** immediately after `runtime_backfill` raised the claude_code ingest depth from 50 to 1088 sessions. The new session was born 2m18s into that blind window, so no amount of clicking Refresh could have produced it. The same staleness was also hiding sessions that had been running for hours: on that node a live probe found **22 running Claude Code processes while Guard listed 11**, so 12 live agents had no Kill button at all, and one listed row pointed at a process that had already exited. `POLL_INTERVAL = 15` in `sync.py` describes an intent the cycle has not met in a long time, and coupling the kill switch to it means the one surface that must be real-time is the one furthest behind.
- **What:** `process_control.live_sessions()` reports every session this node can see as a **running process**, read from the per-pid records the runtime writes itself (`~/.claude/sessions/<pid>.json`) off the memoized map #5529 added — 22 sessions in 8ms, with dead pids filtered so a stale record never renders a Kill button attached to nothing. `/api/guard/sessions` merges those into the store rows via `_live_only_rows`, matching on `native_session_id` because store ids carry the `<runtime>:` namespace and the probe reports what the runtime wrote — comparing raw strings would have listed every session twice. A merged row is namespaced like a store row so the id posted back to `/api/guard/control` is identical whichever source it came from, carries the runtime's own session name as its title rather than a bare uuid, and is stamped `pending_ingest` so the Cost column renders "—" instead of a `$0.00` that would read as measured. Sorting gains recency as its **last** key: money still decides the top of the table, so a just-started session rises to the top of the unflagged group without ever burying a $170 loop. Coverage is stated, not implied — only runtimes in `LIVE_PROBE_RUNTIMES` are listed, because a cwd+argv runtime can be checked but not enumerated without a full process walk, and a probe that silently covered one runtime while implying it covered all of them would be worse than one that says which it covers. A probe that throws costs the extra rows, never the tab.
- **Free-tier follow-up (same PR):** de-duplication was first keyed on the store row's runtime label, which `_session_runtime` resolves through `waste_flags.runtime_from_session_id` — a function that returns `"openclaw"` for every id unless clawmetry-pro is installed. On a Free install the key therefore never matched and the probe listed **every Claude Code session twice**. It passed on a Pro laptop and was caught only by CI, which runs OSS-only. Matching is now against the store's raw ids in both the bare and namespaced spellings and never asks a row what runtime it is.
- **Verified:** 9 tests in `tests/test_guard_live_probe.py`, 7 of which were proven red against unfixed `origin/main` (the eighth is the no-duplicates guard, which passes trivially when there is no probe at all). End to end against this machine's real processes: `live_sessions()` returned 22 live sessions in 8.0ms, and `/api/guard/sessions` went from 11 rows to **23** (12 from the probe) in 94ms with **0 duplicate ids** and flagged sessions still ranked on top. `tests/test_guard_live_probe.py` joins the moat-tests CI job and `make test-moat` alongside the guard tests; the existing 90 guard + process-control tests still pass.

### Perf: session phase and session context rows are written only when they change (#5528) (2026-09-05)
- **Why:** after #5496, #5498 and #5500 the one table on a real node still carrying many dead versions per live row was `session_phase` (12 per row eleven minutes after a compaction): the daemon records every session's phase on every tick, and an upsert that changes nothing is still a DELETE plus INSERT on a keyed table. `session_context` had the same shape at two versions per row, because the family ingest re-delivers every context row each time it re-reads a session.

Both honour `CLAWMETRY_UPSERT_DEDUPE=0`.
- **Verified:** 7 tests in `tests/test_store_phase_context_dedupe.py` (same phase on the next tick writes nothing; a changed phase or cwd writes and moves the stamp; the freshness floor refreshes `observed_at`; dedupe survives a restart; context re-delivery writes nothing; a later occurrence bumps turns and a first summary is kept; kill switch). 4 of them fail on the unpatched store.
