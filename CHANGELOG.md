### Fixed: a correct emailed code dropped you back on "Sign in to open the dashboard" (2026-09-12)
- **Why:** a paying customer reported it after reinstalling: enter the email, enter the code from the email, and the local dashboard shows the sign-in card again, every time. The login wall accepts only the gateway token. Email sign-in succeeded against the cloud but handed the page no credential: it cleared the signed-out marker and reloaded, relying on zero-click `/api/auth/detected-token`. That endpoint refuses unless every strict loopback check passes (client address, Host header, no proxy headers, loopback bind). Wherever one of them fails, zero-click fails on every load, so a correct code reloaded into the same wall forever.
- **What:** `/api/cloud-cta/verify-otp` returns `dashboard_token` when the request passes that same strict loopback check, or when the account that just verified is the account this machine was already linked to (compared in constant time against the key on disk before pairing). The sign-in card stores it before reloading. With no token it tries zero-click once and otherwise says why the dashboard did not open instead of reloading.
- **Not widened:** a proxied or DNS-rebound page that signs in with a different account gets no token, and an unlinked machine off strict loopback gets none either.
- **Verified:** `tests/test_verify_otp_opens_dashboard.py` (6 tests), 4 red on `main` before the fix (the two "no token" cases hold on both sides by design); 48 passing across the verify-otp, OAuth and login-overlay route suites; `node --check` on `auth-bootstrap.js`. Contract recorded in the Cloud Fleet Service blueprint.
- **Not changed:** the Google/GitHub sign-in buttons reload the same way and are the obvious follow-up.
- **Carries:** #5918.

### Fixed: the hosted Activity Heatmap was a grid of zeros, for everyone (2026-09-12)
- **Why:** reported with screenshots for two runtimes on the same node (Claude Code, 2237 sessions; Codex, 25) - the Cost tab's heatmap drew an empty calendar on `app.clawmetry.com` while the same card on localhost was full (`max 1866`). Not a data problem: `clawmetry-cloud`'s `/api/heatmap` handler *built* a 7x24 block of zeros and returned it, and had since the events read was removed (epic #1032). Its comment said the grid would stay empty "until the heartbeat-piggyback path supplies bucketed activity counts". Nothing ever did, and cloud cannot - it holds an opaque encrypted blob by design.
- **What:** the daemon, which is the only side that can count, now ships the finished grid in the E2E snapshot as `activityHeatmap` (per-hour event counts, node-wide and per runtime, 30 days). `clawmetry-cloud#2416` decrypts and draws it client-side.
- **Aggregated in SQL:** `LocalStore.activity_heatmap(days, runtime)` buckets with one `GROUP BY`. The route used to pull up to 50k raw event rows through the daemon proxy and loop over them in Python - tens of MB marshalled per render, and a cap that silently emptied the oldest days of a busy node's 30-day window. `activity_heatmap_by_runtime` gets every runtime plus the node-wide grid in ONE scan, so the snapshot slice costs one query per cycle, not N+1.
- **Hours are node-local:** `cost_windows.hour_expr_sql` / `local_hour`, the hour twins of ADR-046's day bucket. The old path stripped each row's offset before bucketing, so a UTC-writing runtime's afternoon was drawn in the small hours.
- **Scoped by runtime:** `/api/heatmap?runtime=` filters by session-id prefix and app.js sends the active runtime; an unrecognised runtime returns zero, never the node-wide total. The legacy file scan reads OpenClaw logs only, so a runtime-scoped request that reaches it returns the empty grid in shape rather than OpenClaw's hours under a Codex heading.
- **Verified:** `tests/test_activity_heatmap_runtime_scope.py` (5 tests: a UTC-stamped and a local-stamped event at the same instant sharing one cell, prefix scoping, an unknown runtime returning zero, the split reconciling with the single-runtime query, and the grid keeping a fixed 30x24 shape), wired into CI's MOAT verifier job by name.
- **Carries:** #5904.

### Fixed: the cloud strip said "waiting 2h 2m" for a question asked minutes ago (2026-09-11)
- **Why:** `sync._seconds_since` stripped the `Z` from a timestamp and compared it against local wall-clock. Hook-parked approvals are stamped in UTC, so on a CEST machine `deviceSummary.approval.waiting_seconds` was two hours too long from the moment a question was asked, and each new question looked like the old one coming back.

### Fixed: a decision made on a cloud surface now reaches the agent in time (2026-09-11)
- **Why:** the question-set work shipped and was tested live. The cloud strip rendered Claude Code's question with its real options, the click reached cloud in 10 ms with 22 s left on the window - and the agent never got the answer. The relay queue is drained ONLY by a daemon heartbeat, and the main loop heartbeats at the END of a cycle: that node's heartbeats were 20:45:35 then 20:47:05, a 90-second gap spent syncing 7,388 events. The answer landed 5 s after the 20:47:00 deadline, the question had already fallen back to the terminal, and the person's answer reached nobody. `_ingest_keepalive_heartbeat` is 20 s-throttled and only fires inside heavy per-item loops; the 2 s "approvals watcher" scans tool calls, it does not heartbeat. On a busy node, answering from a dashboard was a lottery - for Approve/Deny just as much as for a question.
- **What:** `_answer_window_open()` asks whether any pending approval is still inside its window (`args.deadline_ms`, stamped by the gate-hook receiver); `_start_answer_window_heartbeat()` runs a daemon thread beside the approvals watcher that heartbeats every 2 s while that is true, so a relayed decision reaches the waiting hook in seconds rather than whenever the node next finishes a cycle.
- **Silent when nobody is waiting:** a request without a deadline carries no runtime clock and never holds the fast path open; the tick does nothing without a cloud account or in local-only mode, and costs one indexed read of the pending queue otherwise.
- **Verified:** `tests/test_answer_window_heartbeat.py` (13 tests: window open / passed / decided / no deadline / empty queue / binary request, the tick's four silences, a busy store never raising, and the thread beating repeatedly then stopping), wired into CI's store-invariants job.
- **Carries:** #5883.

### Added: Queue Lanes, so background runs have somewhere to be seen (2026-09-11)
- **Why:** OpenClaw records every background run in one ledger, where the `runtime` column IS the queue lane: `cron`, `subagent`, `cli`. ClawMetry has mirrored that ledger into DuckDB and served it at `/api/run-ledger` since #2100, but PR #5668 removed the unreachable "Sub-Agents and Queue Lanes" tab and took the endpoint's only consumer with it. Measured on `main` before this change: zero references to `run-ledger` across `static/js/app.js` and every shipped tab template. The store query, the endpoint, the snapshot slice and their tests shipped in every wheel with nobody able to see any of it.
- **The cost of that:** a lane can fail wholesale in silence. On the node this was built against, 104 of 106 cron runs had failed over days with `heartbeat skipped: no-route`, and no screen in the product said so.
- **What:** a Queue Lanes rollup inside the existing Crons tab, not a tab of its own: `cron` is one of the three lanes, Crons is already in the nav, and a rollup is a panel's worth of content. Per lane it shows running, queued, succeeded, failed, total and last activity, and states the proportion in words when a lane is mostly failing.
- **The empty state says it has finished, and why:** `/api/run-ledger` deliberately never raises, so a fresh sync, an OpenClaw predating the ledger and a daemon mid-restart all return empty lists. The panel names both real causes instead of spinning. A spinner over an empty ledger is what got the predecessor tab hidden in `44acaa72f` and what put six dead panels on the cloud Security tab.
- **A failed fetch is never reported as an empty ledger:** the error path says the load failed and offers a retry, rather than claiming the node has no background runs because a request timed out.
- **Cloud reads the snapshot:** on the hosted server `/api/run-ledger` is an oss-passthrough with no local DuckDB behind it, so the hosted panel reads the `runLedger` slice of the decrypted snapshot the daemon already emits. Fetching the endpoint there would paint an empty panel over a node that has runs.
- **Also corrected:** `routes/scheduler.py` documented only `~/.openclaw/tasks/runs.sqlite`. OpenClaw 2026.6.5+ moved `task_runs` into the unified `~/.openclaw/state/openclaw.sqlite`, which is why that directory does not exist on a current install; `sync._openclaw_task_ledger_paths()` already read both.
- **Verified:** `tests/test_queue_lanes_panel_is_reachable.py` (8 guards), proven red against `main` before being trusted and green after, and wired into the `ci.yml` lint job by name. Rendered live in a browser on a node running OpenClaw 2026.9.3, reached by `loadCrons()` with no manual call. CI test-coverage ratchet tightened from 932 to 931.
- **Carries:** #5721 (PR #5865).

### Fixed: `save_state` could stall the sync daemon's `last_sync` forever (2026-09-11)
- **Why:** field failures #5853-#5858 reported `daemon_ingest_stalled` across six more OS/Python combinations, the third occurrence of this class after #5800/#5801 and #5829-#5834.
- **The bug:** `run_daemon()`'s steady-state loop wraps almost every ingest call in its own `try/except` so one bad source cannot take the whole cycle down, but `save_state(state)` (the call that actually persists `last_sync` to `~/.clawmetry/state.json`, which `field_report.last_sync_age_secs()` reads) still ran bare. ### Added: Guard notices unrelated agents acting in step, `coordinated_action` (2026-09-11)
- **Why:** rows 5 and 11 of the Hugging Face swarm scorecard: about 1,200 agents used one shared Artifactory path as a message board, then 90% converged on one target within an hour. Every ClawMetry detector read one session, so each agent looked at most slightly odd and the population was invisible. The follow-up post (clawmetry.com/blog/observe-the-swarm-not-the-session) committed to asking the fleet question instead: are sessions that should be independent behaving as if they are coordinated?
- **What:** `clawmetry/detector_swarm.py` turns every write call into a fingerprint (verb, host, first two path segments, digit segments masked, so per-agent directories collapse into the shared board), and groups sessions into families through the subagent table, so an orchestrator and its subagents count once. One finding per fingerprint when at least 5 unrelated families (`CLAWMETRY_COORD_MIN_SESSIONS`) share an action the node has no settled memory of.
- **Unusual means unsettled:** an action counts as normal only after it has been in memory for the settle window (`CLAWMETRY_EGRESS_SETTLE_HOURS`, 24h); a first sighting inside the window stays unusual, so a swarm cannot vouch for itself. A node without a full window of memory reports nothing, because on day one every action is new.
- **One message, every row:** a person gets one alert per fingerprint however many sessions share it; each participating session still shows the finding on its own Guard row. A policy must name `coordinated_action` to act on it, so a catch-all rule written about single agents cannot pause every participant at once.
- **Storage:** `guard_action_fingerprints` (verb, host, two masked path segments, session count, first and last seen; no command text or query strings), pruned with the Guard baseline.
- **Verified:** `tests/test_detectors_coordinated_action.py` (26 tests, including a parent cycle, a settled action, no-memory silence, and a daemon pass that pages once and marks every participant); worst case on 400 real sessions with no history and memory forced old: 0 findings even at a threshold of 2.
- **Not claimed:** correlation of reads, or across machines. No enforcement by default.
- **Carries:** #5846.

### Added: Guard sees write direction, credential values and remote privilege (2026-09-11)
- **Why:** the Hugging Face swarm scorecard (clawmetry.com/blog/could-clawmetry-have-caught-the-hugging-face-swarm) found five things a single swarm member already showed that the behavioural detectors could not see: WebDAV `MKCOL`/`PUT` to an Artifactory host every session was allowed to reach (row 2), an upload to huggingface.co (row 10), Hugging Face write tokens read from output and posted to a board (row 9), admin minted through a token endpoint (row 3), and cluster-admin (row 12). `network_egress` keyed on host only, so a read and a write looked identical; `credential_access` matched secret locations only (0 of 45 values in the vendored corpus); `privilege_change` knew the local OS only.
- **Direction:** each shell segment is classified as a read or a write (curl method or body flags, matched case-sensitively so `-x` and `-f` stay reads and `-G` stays a GET; wget `--post-*`; httpie; `twine`/`npm`/`hf`/`cargo`/`gem` publish; `s3`/`gs` copies and scp/rsync by destination; HTTP tools with a `method` argument). An upload that names no URL is still egress. `network_egress` gains the `write_to_read_only_host` ground: a write to a host the cohort has only ever read from. `guard_egress_hosts` gains `writes`, `write_first_seen` and `dir_since`.
- **Two clocks keep it honest:** a host is read-only only once its direction has been watched for the settle window (existing rows migrate with `dir_since` empty, so an upgrade cannot flag every host), and a first write inside the window does not count, so a swarm's first writer cannot vouch for the rest.
- **Credential values:** token shapes (Hugging Face, GitHub, AWS, Google, OpenAI and Anthropic, Slack, Stripe, JWT, PEM, and the pipelock-community DLP rules ported with a left boundary) in call arguments, heredocs included, and in tool output. Only the category is recorded. Sent to a host that does not own that kind of token, or found in output and then sent anywhere: critical. Placeholders such as `AKIA...EXAMPLE` and kebab-case slugs are rejected.
- **Remote privilege:** role bindings, `system:admin`/`masters` impersonation, AWS IAM key and policy grants, GCP and Azure role grants, privileged or host-root-mounted containers, and writing calls to Artifactory token and plugin and Jenkins script-console endpoints. All critical; reading or listing the same resources stays quiet.
- **Verified:** `tests/test_detectors_swarm_gaps.py` (62 tests); the pipelock corpus value lane moved from 0/45 to 45/45 with 0 near-miss over-fires (`VALUE_LANE_BASELINE` updated deliberately); 0 findings from any new lane across 400 real sessions (13,434 steps) on a development machine.
- **Not claimed:** writes or credentials a program handles internally. These read tool arguments and tool output, and every finding says so.
- **Carries:** #5845.
### Fixed: a critical hook finding named the wrong runtime and the wrong event (2026-09-11)
- **Why:** detection was already correct; the finding it produced was not, and both errors pointed the operator away from the real risk. `_AGENT_HOOK_FILES` mapped each hook file to exactly one runtime, so `.claude/settings.local.json` was always attributed to `claude_code`. But Cursor Desktop reads that file and executes hooks registered there without consent (CVE-2026-48124 / GHSA-pc9j-3qc2-95wv, patched in Cursor 3.0.0). On a Cursor-only machine the `critical` therefore read *"run inside your claude_code session, on every matching tool call"*; an operator who does not run Claude Code dismisses that on entirely reasonable grounds, and the lifecycle was wrong too: the CVE's vector is a `Stop` hook, which fires once at end of turn.
- **What:** a hook file now maps to the **set** of runtimes that execute it, and which one to name comes from the session's own runtime, already passed to `scan_agent_hooks`, so no probe and no new dependency. A session whose runtime reads the file is named directly (*"your cursor session"*); a session that does not read it gets every reader listed (*"read and executed by Claude Code and Cursor"*) rather than one picked arbitrarily. The event name is taken from the hook entry instead of assumed.
- **Verified against a real workspace** carrying a `Stop` hook in `.claude/settings.local.json`: a `cursor` session is now told *"run inside your cursor session, on the `Stop` event"*; `claude_code` names itself; `codex` and an unknown runtime both fall back to naming every reader. On `main` before this, the same file mapped to `claude_code` alone and the sentence said *"on every matching tool call"*.
- **Verified:** 50 tests in `tests/test_guard_workspace_kinds.py`. Carries #5820, closes clawmetry-pro#237.

### Fixed: the stall detector called every sleeping laptop broken (2026-09-11)
- **Why:** the daemon stall reporter shipped in 0.12.855 immediately produced 8 distinct installs and 9 events in under a day, across Darwin and Linux and five Python versions. Against the one bootstrap signature that has 1 install in 30 days. Six issues were auto-filed overnight (#5829–#5834). The volume was the tell: the reports were not trustworthy.
- **The bug is in the clock.** `last_sync` is a **wall-clock** stamp and the check was `now - last_sync > 3600`. Wall-clock elapsed time cannot distinguish "the ingest loop is wedged" from "this machine was not running", so two entirely healthy cases reported as broken: a laptop suspended overnight wakes with an age of hours while the next cycle completes seconds later (the watchdog ticks within 30s of wake, before it lands); and a daemon that just started on a machine powered off overnight reads yesterday's `last_sync`. Every node auto-updates from PyPI, so **every daemon restarted when 0.12.855 shipped**, which is when the reports began. 6 of the 8 installs were Darwin. Laptops sleep.
- **What:** the watchdog now records which `last_sync` value is current and the `time.monotonic()` reading when it first became current. `monotonic()` does not advance across suspend on Darwin or Linux, so "how long have we been watching this same stamp *while actually running*" is the honest measure. Both clocks must exceed the threshold before anything is reported, and a completed cycle restarts the window.
- **No observation history means no report.** A daemon that has just started has no idea, and no idea is never "broken". The same rule `last_sync_age_secs()` already applied to a node that has never synced.
- **The cost, stated plainly:** a genuinely wedged loop is now reported an hour after the watchdog starts watching rather than immediately at process start. That is the right trade. The detector's own definition is "no cycle completed in an hour", and an alarm that fires on healthy machines is one people learn to ignore. Precisely the failure this pipeline was built to prevent.
- **Verified:** four tests, three new, each proven red against the pre-fix code. The slept-laptop case, the just-restarted case, and the completed-cycle window restart all fire a report without the guard. 27 pass in `tests/test_daemon_field_report.py`.
- **Not claimed:** that sleep explains all eight reports. It could not be reproduced locally (that machine runs `caffeinate` and has never slept). The change is correct either way: noise stops, and anything real keeps coming and now means something. Carries #5836.

### Fixed: a blocked agent now reaches a person, and the gate hook cannot fail closed (2026-09-11)
- **Why:** ClawMetry's own Claude Code pre-tool hook blocked every tool call for about six hours, and nobody was told. At a daemon restart the gate installer fell back to `python -m clawmetry`. The daemon ingested both hook errors, but `blocked_on_user` did not treat a hook-rejected call as blocked, and the only channel needing no setup was an in-app banner.
- **Detect:** `blocked_on_user` gains a hook path. - **Prevent:** the gates' `-m` fallback runs isolated (`-P` on Python 3.11+, `-I` otherwise unless clawmetry is a user-site install), so a checkout in the agent's working directory can never shadow the package. Existing hook entries are replaced in place on the next installer pass.

### Fixed: "Still running" was true for 3 of 43 sessions (2026-09-10)
- **Why:** the Sessions list called a session "Still running" when its transcript had a recent event and no end marker. Family runtimes emit no `session.ended`, so that label was stamped once at ingest and never re-examined. A terminal nobody had touched in nine hours read as working. The transcript cannot answer the question, because the question is about a live process.
- **What, and where:** `clawmetry/process_control.py` gains `session_live_state(runtime, session_id)`, which probes the process and returns `busy`, `idle`, `dead`, or `None`. `clawmetry/outcome_classifier.py` gains `classify_session(live=...)`, which takes that verdict as a value and stays pure. It mirrors the `LIVE_*` strings rather than importing `process_control`. `clawmetry/local_store.py` calls the probe and enforces the 10s staleness rule below; `clawmetry/insights.py` excludes in-flight labels from the problems dashboard; `clawmetry/static/js/trail.js` renders the new label.
- **`idle` is not `busy`, and conflating them was the bug.** `busy` covers both "the model is generating" and "a tool call is in flight" (a running Bash tool is work, not waiting. `idle` means the prompt is open and the agent is waiting on a person. `clawmetry/static/js/trail.js` renders that state as **"Waiting on you"**, visually distinct from "Still running") a different statement, and the one that actually tells a person to act.
- **`None` means "cannot tell" and stays distinguishable from `dead`.** Only runtimes that publish a per-pid record can be probed; for everything else the honest answer is unknown and the caller falls back to its time-based heuristic. Reporting `dead` for a runtime we merely cannot see would retire live sessions. Strictly worse than the bug being fixed. A sub-agent row (`<parent>::agent-<id>`) also answers `None`: it has no pid of its own, so the parent's liveness says nothing about whether the child finished.
- **The session id's own prefix wins over the caller's `runtime` argument.** The store prefixes family ids (`claude_code:<uuid>`) while the per-pid maps are keyed on the bare id, and the sessions table stamps `agent_type` `openclaw` on those rows because family ingest sets none. Trusting the argument would make every family session unprobeable. The same mistake that left Guard's controls inert on every family runtime (#5551).
- **A probed verdict is near-certain; a time-based guess is not**. Confidence 0.95 versus 0.6, so a reader can tell a measurement from an estimate. The probe never raises: one that throws is worse than one that shrugs.
- **In-flight labels expire rather than being re-stamped on a schedule.** `ongoing` and `waiting` are statements about a process and go stale the moment it exits; every other outcome describes a transcript that will read the same tomorrow. A stored in-flight label older than 10s is re-resolved on read by `clawmetry/local_store.py` (`_LIVE_LABEL_TTL_MS`, `_is_stale_classification`, `_probe_session_live`). The Guard tab already took the re-stamp approach and was wrong by up to a whole sync cycle. 60–78s normally, 288s behind a backfill.
- **`waiting` joins the outcome enum and is excluded from every finished-session rate**: a session sitting at its prompt is no more a success than one mid-turn. That exclusion is applied in `clawmetry/insights.py`, which drops both in-flight labels from the problems dashboard so a session waiting on a person is never counted as a failure.
- **Recorded in the product record.** Drift Bot found eight, all the same omission. A substantial new capability with nothing written down. The Runtime and Session Observability blueprint now carries ten contracts and an ADR for why an in-flight label expires instead of being refreshed on the sync cycle.
- **Verified:** 54 tests across `tests/test_session_live_state.py` and `tests/test_outcome_classifier.py`, named in `ci.yml`. Carries #5564.

### Added: the daemon reports the failures that stop it working (2026-09-10)
- **Why:** the field-failure pipeline had exactly one producer, and it was the installer. The daemon (which runs on every node and is the single point of failure for all of a customer's data) reported nothing at all when it could not run. Burned 2026-09-08: a Pro node's daemon was locked out of its own pid lock and retried every 30 seconds for twelve hours. It exited 0 each time, so launchd recorded twelve hours of successes; the DuckDB error handler and the auto-updater both initialise *after* the lock is claimed, so neither ever ran; and with no daemon there was no heartbeat, so the node simply went quiet. Quiet is not an alarm, and that customer's dashboard was serving stale data the whole time.
- **What:** `clawmetry/field_report.py` makes the daemon the pipeline's second producer. `daemon_lock_refused` is raised from `run_daemon()` immediately **above** the pid-lock gate (the whole point, since everything that could have reported this lives below it), and only when a sync has not completed for longer than `_STALLED_INGEST_SECS`, so a healthy handover between two daemons is not an incident. `daemon_ingest_stalled` comes from the lock-heartbeat watchdog thread.

The body carries a random install id, a closed-enum failure class, the version, OS name and version, architecture and the interpreter's major.minor. Never a path, username, hostname, node id or log text. `sync.log` stays on the machine. `daemon_failure_payload` is pure, so the contract is asserted key by key over the serialised body.
- **Reporting is not repair.** It changes no agent, no store and no process. At most one report per class per 6-hour window, stamped to a file *before* the send, because the failure being reported is a restart loop: a post that burns its timeout must not let the next restart try again 30 seconds later. It never raises and never blocks the daemon. The stall check runs in the watchdog thread, where an exception would cost the daemon its lock.
- **The dedupe key now carries the stage.** `/api/desktop/_failures` groups by stage × class × OS × Python, but the issue title carried only class/OS/Python, so a daemon that stopped ingesting and an install that never started produced *the same title*, and the second would merely "refresh" the first under a lede describing the wrong failure. A non-bootstrap stage now prefixes the title; `bootstrap_failed` keeps its historical shape byte for byte, because renaming it orphans every open issue.

That ordering is deliberate: a sink accepting a stage nothing sends is harmless; a producer with no sink posts into a silent drop.

### Security: the Werkzeug debugger no longer follows you onto the network (2026-09-10)
- **Why:** `_run_server` called `app.run(..., debug=True, ...)` unconditionally, and two defaults turned that into real exposure rather than a theoretical one. `--debug` is `store_true, default=True`, so dev mode is what you get unless you ask for `--no-debug`; and the startup banner advertises the LAN and public URLs, so reaching the dashboard from another machine means adding `--host 0.0.0.0`. Do both (which the product invites), and any unhandled exception serves Werkzeug's interactive traceback page, with source, local variables and a PIN-gated eval console, to whoever reached the port. This is bandit B201, HIGH.
- **What:** the debugger is enabled only on a bind proven to be loopback. `helpers/server.is_loopback_host` fails closed (anything it cannot positively prove is loopback reads as remote), and accepts `localhost`, IPv4/IPv6 loopback literals, a bracketed `[::1]` and a zone-suffixed form. `0.0.0.0` and `::` are wildcard binds covering every routable interface and are correctly NOT loopback. Hostnames are never resolved to decide this: a name that resolves to loopback today can resolve elsewhere tomorrow, and DNS is not a thing to trust when the answer decides whether to expose an eval console.

### Fixed: every OpenAI session reported the wrong cache-hit rate (2026-09-10)
- **Why:** the two providers count cached tokens differently and one denominator was applied to both. Anthropic reports cached tokens ON TOP OF uncached input, so the rate is `cr / (in_t + cr)`. OpenAI reports them ALREADY INSIDE `input_tokens`, so the rate is `cr / in_t`. Using the additive form for OpenAI understates every figure, and not by a rounding margin: on a session with 100,000 input and 80,000 cached, the true answer is **80.0%** and the old formula returned **44.4%**. That reads as "caching is barely working" for a session where it was working nearly perfectly, which is the kind of number a reader acts on.
- **What:** `_session_cost_intel` resolves the provider from the model through `providers_pricing.provider_for_model`, the one place model-to-provider is decided, so this cannot drift from pricing. OpenAI takes the inclusive denominator, every other provider the additive one, and a provider that cannot be resolved degrades to the additive form, which is the majority case and the historical behaviour.
- **An impossible counter omits the figure rather than reporting it.** For OpenAI, cached tokens are a subset of input, so `cr > in_t` cannot happen. Where it does, `cacheHitPct` is absent from the payload rather than emitted above 100%. A reader can tell "not measured" from "measured and poor"; a 137% cache-hit rate teaches them to distrust every other number on the screen.
- **Recorded in the product record.** The Cost and Efficiency Analytics blueprint already documented the cache-token semantics and never the arithmetic that follows from them, which is exactly where the wrong denominator lived. It now states the derivation per provider, the single source for provider resolution, and the impossible-counter rule, with an ADR recording that a derived metric belongs in the record and not only its inputs. Placed at the top of that blueprint, per its own standing note that an appended section sits past the window a reviewer reads and is treated as absent.
- **Verified:** `tests/test_session_cost_intel.py` pins all three cases, OpenAI inclusive (80.0%), Anthropic additive (44.4%), and the impossible OpenAI counter omitting the key, and is named in `ci.yml`. Closes #5609.

### Fixed: a recycled pid locked the sync daemon out of its own lock (2026-09-09, shipped 0.12.845)
- **Why:** a Pro node stopped syncing at 2026-09-08T19:32 and never resumed. launchd (`KeepAlive`, `ThrottleInterval 30`) respawned the daemon roughly 1,400 times overnight; every one of them printed "Another instance is already running. Exiting." and quit. Reported by email with a `clawmetry status` screenshot, which is the only way it could have been reported: that screen showed "Cloud sync: Connected", "Runtimes: watching", "Daemon: Running (launchd)" and a bare 12-hour-old "Last sync" with no comment on it.
- **The log looked like a healthy restart and was not.** The tail read "Another instance ... / raised RLIMIT_NOFILE 256 -> 4096 / Another instance ...", which reads as a daemon that started at midnight. The fd limit is raised in `run_daemon()` *before* `_acquire_pid_lock()`, so that line is not evidence of a start. The whole tail is one loop body repeating every 30 seconds.
- **Cause:** `_acquire_pid_lock` asked one question, is the pid in `sync.pid` alive. A pid is not an identity. A daemon that dies without running its atexit hook (SIGKILL, panic, power loss, and the spawn race in #5740) leaves the file behind, and the OS eventually hands that number to an unrelated process. `is_alive()` then answers yes forever and there is no way back except a human deleting the file. `clawmetry sync --restart` does not clear it either: nothing outside `sync.py` ever removes that file.
- **The guard already existed and was not called.** `process_control.verify_pid` is the pid-reuse guard every Guard actuator runs before it signals anything. The lock now uses it: identity is `(pid, start-time token)`, recorded in a `sync.lock.json` sidecar so `sync.pid` stays a bare int for `daemon_registration._is_sync_running`, the dashboard's background spawn and `install.sh`'s sandbox teardown, none of which had to change.
- **Three fallbacks, because the primitive is not available everywhere.** A legacy bare-int file has no token, so: a holder whose start time is AFTER the lock file's mtime is proof of reuse needing no command line (the only check that works on Windows without psutil, via ctypes `GetProcessTimes`); otherwise a command line that is readable and foreign condemns it (macOS and Linux, where `ps` always answers); and "I could not look" is a distinct verdict that fails CLOSED, so an upgrade on a Windows host never reclaims a lock a healthy daemon still holds.
- **A wedged holder is handled separately and conservatively.** A watchdog thread ticks `sync.heartbeat` every 30s, deliberately independent of the ingest cycle so a slow backfill keeps its lock; a holder that is genuinely ours but has stopped ticking for `CLAWMETRY_LOCK_STALE_SECS` (default 900) is stopped and taken over. Only a heartbeat that EXISTS and went stale condemns anyone, so upgrading never shoots a healthy daemon from a release that predates the file.
- **Status stops reporting health it has not checked.** `launchctl list` exits 0 for a job that is merely REGISTERED, so a restart loop rendered as a green tick; the daemon line now reads the `PID` key and says "Set up but not running right now (launchd keeps retrying)". `Last sync` carries its age and says when nothing is new. A stalled node gets one plain sentence naming the command that fixes it, and when the log carries the lock-loop signature it names that cause specifically. Everything above that line reports how the node is CONFIGURED; nothing on the screen reported whether data was moving, which is why a paying customer had to tell us.
- **The fix is only half of it, and the other half is tracked.** Nothing here would have told US. Every self-repair mechanism the daemon has (the DuckDB error handler, the auto-update worker, the install ping) initialises AFTER the lock is claimed, so a daemon that cannot start runs none of them; it exits 0, so the supervisor counts successes; and with no daemon there is no heartbeat, so the node goes quiet, and quiet is not an event. #5752 makes the daemon a producer on the field-failure pipeline that already exists, so the next node in this state files itself as an issue instead of arriving by email.
- **Verified:** the customer's machine reproduced on both trees, a `sync.pid` naming a live unrelated process. On `origin/main` the lock is refused and the daemon quits; on this change it logs `reclaiming stale sync.pid (pid_recycled(cmdline_mismatch))` and starts. `tests/test_pid_lock_reclaim.py` (14), and `tests/test_status_daemon_truth.py` (14), named in `ci.yml`, proven red on the unfixed code. `tests/test_pid_liveness_windows.py` keeps passing; its stand-in sleeper now has to look like the daemon, because a bare sleeper is exactly the recycled pid this stops trusting. Carries #5745.

The root-span heuristic that was the alternative would have missed 15% of traces outright, since only 226 of 265 carry a root span. The trace-id fallback does not invent a mapping, it reproduces the one conforming exporters already produce.
- **Stated honestly:** that node has exactly one sessionless span, our own CI smoke, so sessions per hour for existing pushed OTLP sources goes from 0 to 0 and there is no installed base there to regress. One node cannot speak for an install actually pointing OpenLLMetry at us, so the regression guard comes from the pinned test, not from the measurement alone.
- **The obvious key would have been a bug.** `otlp:trace:<id>` was the natural shape and is wrong here: every session-id parser in the codebase (`_sid_runtime` plus its inline siblings in bench, cohort, harness, health and sessions) takes the text before the FIRST colon as the runtime, so that prefix would have filed every derived session under a runtime literally named "otlp" instead of the app's own `agent_type`. That is exactly the mis-bucketing `_otlp_service_name_to_agent_type` exists to prevent, and a breach of the per-runtime honesty gate. The key is `<agent_type>:trace:<id>`: the head makes every existing parser correct for free, and `trace:` as the second segment marks the id as derived rather than sent.
- **Confined to foreign apps.** `agent_type == "openclaw"` is the population the materializer deliberately skips, since those sessions come from transcripts, so minting a key there would put a session id on a span that joins no session: a phantom, a bug shape this repo has shipped before. Those spans keep the null they have today, pinned by its own test.
- **Recorded in the product record, not just the code.** REQ-OBS-RSO-033 previously specified session materialization only for spans that CARRY a conversation or session identifier, so this behaviour would have been an undocumented fallback. It now carries AC-OBS-RSO-033.7 (one session per trace when no identifier is sent, with the measurement that justified it), .8 (a derived identity carries the application's own runtime and is distinguishable from one an emitter sent), .9 (the derivation does not apply to OpenClaw spans, which would otherwise name a session that does not exist), and .10 (an emitter that does send an identifier is unaffected, which is part of the requirement because the path is shared).
- **Verified:** `tests/test_otlp_sessionless_spans.py`, 14 cases through the REAL ingest path (`POST /v1/traces` to `_process_otlp_traces` to DuckDB), named in `ci.yml`. Proven red BOTH ways: removing the fallback reds 11 of 14, and using the `otlp:` prefix reds 8 of 14, so the mis-bucketing guard is load-bearing rather than decorative. The three that pass either way are the regression guards. 87 tests pass across every OTLP suite in the repo. Closes #5691.
### Added: the workspace scanner reads package.json install hooks (2026-09-08)
- **Why:** same predicate as `.git/config`, different file. A `package.json` lifecycle hook is a program the checkout names and a package manager runs, without consent, during an action the developer thinks is "fetch dependencies". It is the CHAINDROP delivery vehicle, and the red-team audit had already recorded it as a measured MISS: nothing fired at all.
- **Measured before designing, not after.** Across 189 real `package.json` files on a working machine: `prepublishOnly` appears 36 times and `prepack` / `postpack` once each, and **none of them run on install** (they run on publish). `prepare` 7, `postinstall` 4, `preinstall` 3 are the install-time surface. The new scanner over those same 189 manifests reports **0 critical, 8 warning**, which is the same discipline the git-config scanner holds (0 critical, 3 warning across 50 repos).
- **Graded, not binary.** `critical` only for shapes an ordinary build does not have: fetching code and piping it to a shell, decoding a blob, inline `-e`/`-c`, reading a credential file, or reading a publishing token from the environment. - **Shipped with its own cache fix, deliberately.** The first cut of this scanner read `package.json` while the daemon's cache stamp did not, so a checkout that was clean when first seen stayed clean forever no matter what was added to it afterwards. That is the same false-all-clear shape as the linked-worktree gap and it was caught before this released. `repo_scan` now DECLARES `SCANNED_FILES` beside the scanners that read them and the stamp derives from it, so a scanner that learns a new file teaches the cache automatically; the guard walks that same declaration rather than a copy of it.
- **Verified:** `audit.py` 15/15 with a new corpus case whose postinstall reads `~/.npmrc`; reverting `clawmetry/repo_scan.py` alone reds 21 of 59 tests in the corpus file. The JS label guard added with the workspace kinds walked `ALL_INCIDENT_KINDS` and refused to pass until both label maps learned `package_manifest_exec`, which is the anti-drift mechanism working on its first new kind rather than being remembered by a human.

- **Why:** on a real node 2026-09-05 a contended read through the daemon query proxy timed out, and four tabs said the same confident thing at once. Sessions said "No Claude Code sessions have a transcript yet" *under its own header counting 61 sessions*. `/api/model-attribution` answered `{"model_count": 0}` over a store holding thousands of events, `/api/usage/by-plugin` answered `{"plugins": []}`, and the Agents panel said "The AI is idle." When the truth is "I could not read it", that claim is false and is indistinguishable from data loss to the person reading it. The code even predicted it: the comment above `_PROXY_TIMEOUTS` says a contended read can "surface as a transient EMPTY result (urlopen raises, caller returns None, blank tab)".
- **Why it sat unfixed:** the contract already existed. The Cost and Efficiency Analytics blueprint names the field, `store_available`, and review, bench, quality, cohort and the outcome trend already honour it. The blocker was arithmetic. `local_store_via_daemon` has roughly 490 call sites across 46 route modules, and two earlier passes on the issue stopped there, correctly, because converting them piecemeal would miss endpoints and ship the same lie in a different tab.
- **What:** record the fact ONCE and stamp it everywhere. `routes/local_query.py` gains `note_store_unreachable()` / `note_store_read_ok()` / `store_available()`, scoped to the request; `dashboard.py` stamps `store_available: false` onto any `/api/*` JSON object that did not answer the question itself, plus an `X-CM-Store-Available: false` header. A fast path written tomorrow is correct by default, because there is no helper anyone has to remember to call.
- **Deliberately narrow, so the flag means what it says.** Only a round trip we ACTUALLY ATTEMPTED and lost counts: a timeout, a stale port, or a daemon that refused the shape (the issue's second, deterministic reproduction, a dashboard restarted against an older daemon build). No daemon at all, or being the daemon, is the supported direct-open path and does not raise it, or every dev boot and every test run would carry a permanent warning. It only ever adds `false`: a handler that computes the field keeps its own value and a healthy request is byte-identical, so no existing response shape, snapshot slice or parity test moves.
- **The banner reads the HEADER, not the body.** Cloning and re-parsing every API response, including the multi-MB event scans, to find one field is exactly the request-cost regression FLYWHEEL forbids. One header read, no body touched, and it self-heals: the next healthy `/api/*` response clears it.
- **Verified live against a genuinely blocked daemon, not a mock:** a real `local_server` owning a real DuckDB (14 events, 7 sessions), then `kill -STOP`. Healthy, the answer is byte-identical to today (7 transcripts, no flag, no header). Blocked, all five endpoints named in the issue answer `store_available: false`, and Sessions renders the honest sentence with a Retry instead of "No transcript files found". `kill -CONT` restores it with no user action.
- **The live run caught a bug the unit tests could not.** The first blocked run still answered `{"transcripts": []}` with no flag: under a standard install `get_store()` never opens DuckDB, it hands back a `_ProxyStore` that forwards to the SAME daemon, so a dead daemon reaches the "direct-open fallback" as a silent `None` and cleared the very flag the proxy had just raised. Only a non-`None` result proves the store was readable.
- **Cloud is unaffected by construction:** the hosted container has no discovery file, so no round trip is attempted and nothing is stamped.
- **Verified:** 17 tests in `tests/test_store_unreachable_is_not_empty.py`, named in `ci.yml`, each proven to fail against the unfixed code before being trusted. Closes #5534.

### Added: build your own UI, a keyed and scoped read API over the q/1 contract (2026-09-08)
- **Why:** ClawMetry ships one dashboard, and a user who wants a different view of their own data has no supported way to get one. Every number the dashboard draws already comes from a declared, versioned read contract (`q/1`, 17 live methods, per-method arg schemas, additive-only, drift-tested). The only thing allowed to call it was the dashboard itself, because the only gate in front of it was the browser's same-origin rule: there was no API key anywhere, and no `Access-Control-Allow-Origin` header anywhere in the codebase. So the options were fork the dashboard, scrape the HTML, or do without. Meanwhile the generation tools got good enough that a purpose-built view is an afternoon of work *if* the data has an addressable API. Ours did not have a door.
- **What:** four pieces, all built on what already existed. (1) **Read scopes live on the contract**: every `q/1` method now declares one of `read:metrics`, `read:sessions`, `read:traces`, `read:content`, in `clawmetry/query_contract.py` next to its trust class, so a new method cannot drift out of the scope model and `docs/QUERY_CONTRACT.md` regenerates with a scope table. (2) **Scoped keys** (`clawmetry/apikeys.py`, `clawmetry key create|list|revoke|scopes`, and a panel on the Security tab): SHA-256 in `~/.clawmetry/api_keys.json` at 0600, each key carrying scopes and a browser-origin allowlist. (3) **`GET /api/q/1/<shape>`** (`routes/public_api.py`), dispatching through the *same* `routes.local_query._dispatch` the dashboard uses, so there is no second query surface to keep correct. (4) **`GET /api/q/1/llms.txt`**, the whole API written for a coding agent to read in one pass, generated from the contract and scoped to the presented key. Any page in any tab can already *send* a request to `127.0.0.1:8900`; the only reason that has been harmless is that the browser refuses to let the page *read* the reply. This feature removes that protection deliberately, one named origin at a time, so: **loopback earns nothing** (this is the one surface in ClawMetry where "the request came from this machine" is not authentication, and a key is always required); **there is no wildcard origin**, not as a flag and not as an env var, because every "just for local dev" wildcard ships eventually and fails silently and totally; **key management is not on the keyed surface** (minting, listing and revoking sit on the ordinary dashboard blueprint behind the existing same-origin write guard, so a read key can never issue itself a better one, and `_add_cors` is pinned to `/api/q/` as belt and braces); and **the API is GET only**, which removes cross-origin writes as a category rather than as a check. Nothing here can pause, stop or kill an agent: this adds no entry to the control plane.
- **`read:metrics` is exactly the `plaintext` trust class**, pinned by a test rather than by convention. That equality is what makes "a browser-resident key cannot return a prompt, a reply or a file path" a promise instead of a hope, and it is why the starter ships asking for that scope and nothing more.
- **Verified end to end in a real browser, not only in tests.** The starter served from `http://localhost:3000` rendered 30 days of real cost from a ClawMetry on a different port: **$750 across 10 runtimes and 10 models**, the numbers matching `/api/aggregates` on the same machine. Plus **48 guards** in `tests/test_public_api_keys.py` (registered in `ci.yml`, since CI runs explicit file lists), with three deliberate mutations proving they go red: making `_add_cors` echo every origin fails 4, removing the scope check fails 2, and reclassifying `transcript` as `read:metrics` fails 4 including the trust-class invariant. Every drift guard green: query-contract, module map, runtime and channel counts, AC ratchet, daemon allowlist, py3.9 annotations, `lint-js`.

### Perf: session phase and session context rows are written only when they change (#5528) (2026-09-05)
- **Why:** after #5496, #5498 and #5500 the one table on a real node still carrying many dead versions per live row was `session_phase` (12 per row eleven minutes after a compaction): the daemon records every session's phase on every tick, and an upsert that changes nothing is still a DELETE plus INSERT on a keyed table. `session_context` had the same shape at two versions per row, because the family ingest re-delivers every context row each time it re-reads a session.
- **What:** `record_session_phase` hashes the content columns (runtime, phase, status, basis, end reason, resolvable, cwd), and skips the write when the stored row has the same hash and was observed within `CLAWMETRY_PHASE_REFRESH_SECS` (600), so `observed_at` never goes stale for more than that; a phase or directory change still writes and still moves `phase_since` exactly as before. `ingest_session_context` looks up what the table already holds for the batch's sessions once and skips a row whose stored first/last timestamps already cover it and that brings no summary the row lacks; a later occurrence still bumps `turns`. Both honour `CLAWMETRY_UPSERT_DEDUPE=0`.
- **Verified:** 7 tests in `tests/test_store_phase_context_dedupe.py` (same phase on the next tick writes nothing; a changed phase or cwd writes and moves the stamp; the freshness floor refreshes `observed_at`; dedupe survives a restart; context re-delivery writes nothing; a later occurrence bumps turns and a first summary is kept; kill switch). 4 of them fail on the unpatched store. The phase-model, context-ingest, context-route and query-contract suites pass unchanged (75 tests). Wired into the CI MOAT file list.

### Fixed: the hosted session page counted zero messages for every non-OpenClaw runtime (2026-09-11)
- **Why:** a Codex session page on app.clawmetry.com read "Messages 0" beside a transcript the local store counts as 371 messages. The cloud's `sessions` table has no `message_count` column at all: the one count it keeps is `event_count`, and the hosted page renders "Messages" straight from it. The OpenClaw cloud row has always sent that key; the family row (claude_code, codex, cursor, copilot, ...) sent `message_count` instead, which the cloud drops, so the column stayed 0 for every non-OpenClaw session ever synced.
- **What:** the family cloud row now carries `event_count` too, the same raw-row count the OpenClaw path sends. No cloud-side change: the column the page already reads simply stops being empty.
- **Verified:** `tests/test_family_cloud_row_event_count.py` drives the real `sync_family_runtimes` with a fake adapter (4 events, `message_count=2`), captures the cloud push and asserts the row carries `event_count == 4` while `message_count` stays. Runs in CI.

### Fixed: the message count now reaches sessions already recorded (2026-09-11)
- **Why:** 0.12.871 added `event_count` to the family cloud row, the number the hosted session page renders as "Messages". That row is written only when a session is processed, and the daemon skips sessions whose events have not advanced (`family_event_high_water`). So the fix reached a session the next time it grew and no other: every session already recorded kept "Messages 0" indefinitely. Measured live on app.clawmetry.com after 0.12.871: a session still being written showed "Messages 688", while the idle Codex session from the original report still showed 0.
- **What:** the family ingest salt moves to `/t2`, which re-reads each family session once. This is the rule the feature blueprint's ADR-003 states: a change to what ingest writes needs a salt, or it applies to new sessions only.
- **Also:** the test that pinned the exact salt now pins its shape (`t` followed by digits). Pinning the value turns every future bump into a test edit, while the contract worth holding is that a salt is present at all.
- **Carries:** #5894.
