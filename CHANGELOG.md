### Fixed: a pushed OTLP span with no conversation id never became a session (2026-09-08)
- **Why:** `_otel_to_row` read the session id from four attribute keys and had no fallback, and `materialize_otlp_sessions` (WO-55) only ever sees the ids collection gathered. So an exporter that sets `gen_ai.conversation.id` worked, and one that does not landed its spans in `spans` and produced no `sessions` row at all. The data sat in the store and Sessions, Cost and Guard could not see it. Nothing errored, so nothing prompted anyone to look. Nothing in the OTel GenAI convention requires a conversation id, and a plain OTel SDK or OpenLLMetry on defaults sends none, so this is the common case rather than the exotic one.
- **Measured before deciding, which is why two earlier passes stopped here.** On a live node: 265 real traces, and `trace_id` maps to exactly one session on 265 of 265, with no session spanning more than one trace. Traces are RUNS, not tool calls (median 2 spans per trace, p90 231, p90 duration about 2.4 h), so the "one trace per tool call" flood the report feared is not the shape of the data. The root-span heuristic that was the alternative would have missed 15% of traces outright, since only 226 of 265 carry a root span. The trace-id fallback does not invent a mapping, it reproduces the one conforming exporters already produce.
- **Stated honestly:** that node has exactly one sessionless span, our own CI smoke, so sessions per hour for existing pushed OTLP sources goes from 0 to 0 and there is no installed base there to regress. One node cannot speak for an install actually pointing OpenLLMetry at us, so the regression guard comes from the pinned test, not from the measurement alone.
- **The obvious key would have been a bug.** `otlp:trace:<id>` was the natural shape and is wrong here: every session-id parser in the codebase (`_sid_runtime` plus its inline siblings in bench, cohort, harness, health and sessions) takes the text before the FIRST colon as the runtime, so that prefix would have filed every derived session under a runtime literally named "otlp" instead of the app's own `agent_type`. That is exactly the mis-bucketing `_otlp_service_name_to_agent_type` exists to prevent, and a breach of the per-runtime honesty gate. The key is `<agent_type>:trace:<id>`: the head makes every existing parser correct for free, and `trace:` as the second segment marks the id as derived rather than sent.
- **Confined to foreign apps.** `agent_type == "openclaw"` is the population the materializer deliberately skips, since those sessions come from transcripts, so minting a key there would put a session id on a span that joins no session: a phantom, a bug shape this repo has shipped before. Those spans keep the null they have today, pinned by its own test.
- **Verified:** `tests/test_otlp_sessionless_spans.py`, 14 cases through the REAL ingest path (`POST /v1/traces` to `_process_otlp_traces` to DuckDB), named in `ci.yml`. Proven red BOTH ways: removing the fallback reds 11 of 14, and using the `otlp:` prefix reds 8 of 14, so the mis-bucketing guard is load-bearing rather than decorative. The three that pass either way are the regression guards. 87 tests pass across every OTLP suite in the repo. Closes #5691.
### Added: the workspace scanner reads package.json install hooks (2026-09-08)
- **Why:** same predicate as `.git/config`, different file. A `package.json` lifecycle hook is a program the checkout names and a package manager runs, without consent, during an action the developer thinks is "fetch dependencies". It is the CHAINDROP delivery vehicle, and the red-team audit had already recorded it as a measured MISS: nothing fired at all.
- **Measured before designing, not after.** Across 189 real `package.json` files on a working machine: `prepublishOnly` appears 36 times and `prepack` / `postpack` once each, and **none of them run on install** (they run on publish). `prepare` 7, `postinstall` 4, `preinstall` 3 are the install-time surface. So only those four hooks are read; including the publish-time ones would have quadrupled the noise for no coverage. The new scanner over those same 189 manifests reports **0 critical, 8 warning**, which is the same discipline the git-config scanner holds (0 critical, 3 warning across 50 repos).
- **Graded, not binary.** `critical` only for shapes an ordinary build does not have: fetching code and piping it to a shell, decoding a blob, inline `-e`/`-c`, reading a credential file, or reading a publishing token from the environment. Everything else is a `warning` that says what it found, and a recognised tool (husky, patch-package, only-allow, node-gyp, prisma) is NAMED rather than suppressed: husky's mechanism is precisely the one CHAINDROP abused, and "via husky" tells an operator something silence does not.
- **Scope stated where it is missing.** This catches "the repo you cloned runs its own code on install". The poisoned TRANSITIVE dependency, which is where CHAINDROP actually lived, needs the lockfile, and the measurement says that is not shippable: 73 real lockfiles carry 2 to 13 `hasInstallScript` packages each, dominated by `fsevents` and `esbuild`, so an incident per lockfile would be noise rather than a finding. Recorded in the docstring, the blueprint and the requirement rather than guessed at.
- **Shipped with its own cache fix, deliberately.** The first cut of this scanner read `package.json` while the daemon's cache stamp did not, so a checkout that was clean when first seen stayed clean forever no matter what was added to it afterwards. That is the same false-all-clear shape as the linked-worktree gap and it was caught before this released. `repo_scan` now DECLARES `SCANNED_FILES` beside the scanners that read them and the stamp derives from it, so a scanner that learns a new file teaches the cache automatically; the guard walks that same declaration rather than a copy of it.
- **Verified:** `audit.py` 15/15 with a new corpus case whose postinstall reads `~/.npmrc`; reverting `clawmetry/repo_scan.py` alone reds 21 of 59 tests in the corpus file. The JS label guard added with the workspace kinds walked `ALL_INCIDENT_KINDS` and refused to pass until both label maps learned `package_manifest_exec`, which is the anti-drift mechanism working on its first new kind rather than being remembered by a human.

### Fixed: an unreadable local store rendered as "you have no data" (2026-09-08)
- **Why:** on a real node 2026-09-05 a contended read through the daemon query proxy timed out, and four tabs said the same confident thing at once. Sessions said "No Claude Code sessions have a transcript yet" *under its own header counting 61 sessions*. `/api/model-attribution` answered `{"model_count": 0}` over a store holding thousands of events, `/api/usage/by-plugin` answered `{"plugins": []}`, and the Agents panel said "The AI is idle." A spinner says wait and an error says something is wrong, but an empty state is a positive claim about the user's own work. When the truth is "I could not read it", that claim is false and is indistinguishable from data loss to the person reading it. The code even predicted it: the comment above `_PROXY_TIMEOUTS` says a contended read can "surface as a transient EMPTY result (urlopen raises, caller returns None, blank tab)".
- **Why it sat unfixed:** the contract already existed. The Cost and Efficiency Analytics blueprint names the field, `store_available`, and review, bench, quality, cohort and the outcome trend already honour it. The blocker was arithmetic. `local_store_via_daemon` has roughly 490 call sites across 46 route modules, and two earlier passes on the issue stopped there, correctly, because converting them piecemeal would miss endpoints and ship the same lie in a different tab.
- **What:** record the fact ONCE and stamp it everywhere. `routes/local_query.py` gains `note_store_unreachable()` / `note_store_read_ok()` / `store_available()`, scoped to the request; `dashboard.py` stamps `store_available: false` onto any `/api/*` JSON object that did not answer the question itself, plus an `X-CM-Store-Available: false` header. A fast path written tomorrow is correct by default, because there is no helper anyone has to remember to call.
- **Deliberately narrow, so the flag means what it says.** Only a round trip we ACTUALLY ATTEMPTED and lost counts: a timeout, a stale port, or a daemon that refused the shape (the issue's second, deterministic reproduction, a dashboard restarted against an older daemon build). No daemon at all, or being the daemon, is the supported direct-open path and does not raise it, or every dev boot and every test run would carry a permanent warning. It only ever adds `false`: a handler that computes the field keeps its own value and a healthy request is byte-identical, so no existing response shape, snapshot slice or parity test moves.
- **The banner reads the HEADER, not the body.** Cloning and re-parsing every API response, including the multi-MB event scans, to find one field is exactly the request-cost regression FLYWHEEL forbids. One header read, no body touched, and it self-heals: the next healthy `/api/*` response clears it.
- **Verified live against a genuinely blocked daemon, not a mock:** a real `local_server` owning a real DuckDB (14 events, 7 sessions), then `kill -STOP`. Healthy, the answer is byte-identical to today (7 transcripts, no flag, no header). Blocked, all five endpoints named in the issue answer `store_available: false`, and Sessions renders the honest sentence with a Retry instead of "No transcript files found". `kill -CONT` restores it with no user action.
- **The live run caught a bug the unit tests could not.** The first blocked run still answered `{"transcripts": []}` with no flag: under a standard install `get_store()` never opens DuckDB, it hands back a `_ProxyStore` that forwards to the SAME daemon, so a dead daemon reaches the "direct-open fallback" as a silent `None` and cleared the very flag the proxy had just raised. Only a non-`None` result proves the store was readable.
- **Cloud is unaffected by construction:** the hosted container has no discovery file, so no round trip is attempted and nothing is stamped.
- **Verified:** 17 tests in `tests/test_store_unreachable_is_not_empty.py`, named in `ci.yml`, each proven to fail against the unfixed code before being trusted. Closes #5534.

### Fixed: two functions named `_session_cwd`, and the later one silently replaced the other (2026-09-08)
- **Why:** shipped in 0.12.837 and live through 0.12.839. `sync.py` already had `_session_cwd(row)`, a raw adapter/gateway dict read through a **twelve-alias** set (`cwd`, `workingDir`, `workingDirectory`, `workspace`, `workspaceRoot`, `project_dir`, `projectRoot`, `directory`, `folder`, ...). The workspace-scan change added a second function with the same name 2,000 lines below it, reading two keys. Python keeps the last definition and says nothing, so all THREE callers of the original quietly switched: gateway session shaping (`sync.py:4328`), the session row build (`4586`), and the FAMILY ingest cwd (`15293`). That last one writes `sessions.cwd`, which is the column `process_control` promotes to find a pid and the one the workspace scanner keys on, so a runtime that spells its directory `workingDir` or `directory` in metadata stopped persisting it. Nothing failed. The tests passed. Three wheels shipped.
- **What:** the newer helper becomes `_session_row_cwd` (it reads a store ROW: the `cwd` column first, then metadata) and its metadata fallback now DELEGATES to `_session_cwd`, so both paths honour the same alias set. Both are strictly better than before the collision. A second shadowing found by the same walk is also removed: `start_log_streamer` was defined twice, the first an empty docstring-only stub.
- **The guard is the point.** `tests/test_no_shadowed_module_functions.py` walks the AST of every first-party module and fails on a top-level name defined twice. Line coverage cannot see this class, review rarely does in a 25,000-line module, and grep does not either unless you already suspect it. Auto-discovering, so a new module is covered without anyone remembering to add it, and it carries a self-test that it detects a shadow in a synthetic module, because a guard nobody has watched fail is not a guard.
- **It found pre-existing debt, recorded as a ratchet rather than fixed here:** `dashboard.py` carries 59 shadowed names (39 byte-identical dead pairs and **20 that differ**, meaning someone edited one copy and not the other) and `routes/entitlement.py` carries 1. `verification/shadowed_definitions.json` holds those counts; the test asserts a file never rises above its baseline and that each baseline equals reality, so no headroom is left for the next one and the debt can only shrink.
- **Verified:** restoring the old name reproduces `_session_cwd: 2` in the AST walk and reds the guard; with the fix, 235 module files pass and 273 tests pass across the daemon-wiring, detector and workspace-kind suites.

### Fixed: a poisoned linked worktree scanned CLEAN (2026-09-08)
- **Why:** `repo_scan` opened `<workspace>/.git/config` and nothing else. In a **linked worktree** `.git` is a FILE holding `gitdir: /abs/path`, and the config git actually reads lives in the common directory that path points at, so the scanner found no config and returned no findings. That is worse than returning nothing: it is a confident all-clear over a repository git will happily execute `core.fsmonitor` from, on a layout agents and CI use routinely. CVE-2026-55607 is the vendor-confirmed version of the same git-directory confusion. Found by `scripts/redteam/audit.py` itself, which filed the gap automatically: the audit doing exactly the job it was wired into CI for one release earlier.
- **What:** `_git_dirs()` resolves `(git_dir, common_dir)` through the `.git` file's `gitdir:` and the worktree's `commondir`. `_git_config_paths()` returns every config git reads, which is `<common>/config` plus `<gitdir>/config.worktree` (honoured when `extensions.worktreeConfig` is set, and writable by whoever supplied the worktree). The finding reports the config it was actually read from, trimmed to its last three components, because an incident travels to a UI and to a device and must not carry the user's home directory. Ordinary checkouts are untouched: `_git_dirs` answers with `.git` for both values and the label stays `.git/config`.
- **Verified against real git, not a fixture:** the tests build the worktree with `git worktree add`, because the layout git writes is the thing under test and a fixture written from memory passes against a resolver that only handles the layout its author imagined. The first draft of the test asserted the wrong admin-directory name (git names it after the worktree PATH, not the branch), which is precisely the class of detail that would have made a fixture-only test green against broken code. Guard proven to fail: reverting `clawmetry/repo_scan.py` alone reds **9 of 38** tests, including the corpus case and all five malformed-`.git` cases; `audit.py` drops from 14/14 to a MISS, and `control-benign-repo` stays PASS either way, so no false positive was introduced. The corpus materialiser gained `{{WORKSPACE}}` so the new case can carry the absolute `gitdir` git really writes.

### Added: Guard and the policy engine learn the two workspace kinds (2026-09-08)
- **Why:** `repo_scan` emits `repo_config_exec` and `agent_config_tamper` in the same shape as every detector incident, and no surface knew them. The Guard tab printed the raw id, the policy form could not select them, and `detectors.DETECTOR_KINDS`, which exists precisely so a new detector cannot be added without the surfaces that render it noticing, could not see them because they live outside `detectors.py`. Verified live the same day: a real `cursor-agent` session in a repo with a poisoned `.git/config` produced a `repo_config_exec` critical incident that sorted **fifth**, below four money-flagged sessions worth $7.79 in total. That is what "ranked by spend at risk" does to a finding that has no spend.
- **What:** one list, not two that drift. `repo_scan.WORKSPACE_KINDS` is declared where the kinds are produced, re-exported as `detectors.WORKSPACE_KINDS`, and `detectors.ALL_INCIDENT_KINDS` is the union every renderer reads. The Guard policy form is now BUILT from `GUARD_KIND_LABEL` instead of a third hand-typed `<option>` list, which is exactly how a kind ends up renderable but not selectable. A parametrised guard walks `ALL_INCIDENT_KINDS` and asserts plain-words copy exists in both JS label maps, so a kind added later is covered without editing the test.
- **A policy must NAME a workspace kind to act on it.** `trigger_kind: ""` now means "any signal about the agent". Both workspace kinds are `critical` by construction, so folding them into the catch-all would silently repurpose every existing "pause anything critical" rule into one that also pauses sessions over a property of a checkout, with no way to write "except that". That is the shape of the preset that paused 280 sessions in 22 minutes. With that boundary in place the daemon now hands workspace findings to the policy pass, which is what makes a named policy possible at all.
- **Ranking, decided rather than fudged.** A workspace finding gets its own field on the Guard row and its own sort axis ahead of the money key, instead of an invented dollar figure so it would sort well. Inventing one is the thing `annotate_spend` exists to refuse. The row now renders both: what the agent is doing, and what is in the folder it was pointed at.
- **Verified:** guard proven to fail on the unfixed code per property. Reverting the catch-all exclusion reds the two "any signal does not match" cases; reverting the workspace split in `routes/guard.py` reds the field and ordering cases. 40 tests in `tests/test_guard_workspace_kinds.py`, named in `ci.yml` and registered in `verification/guards.json`; 207 pass across the guard, detector and policy suites. Also fixes the same cwd bug in `routes/guard.py` that `sync` had: the row read only `metadata` and ignored the `sessions.cwd` column, which is what `runtime_control_support` promotes to find a pid.

### Added: the daemon scans a session's workspace, which is the surface the tool stream cannot see (2026-09-08)
- **Why:** every behavioural detector reads what the agent *chose* to do. GitSpawn is the proof that this is a partial view of the machine: a poisoned `.git/config` makes **git** spawn the payload during the background `git status` a runtime fires on open, the agent calls no tool, and `detectors.run_all` sees a clean session. `clawmetry/repo_scan.py` closes that gap and has shipped for a while, detecting all three GitSpawn variants plus the CHAINDROP hook shapes, with `clawmetry scan-repo` exposing it to a human. Nothing in the product called it. A detector nobody runs protects nobody.
- **What:** `sync._emit_detector_incidents` now scans each session's `cwd` and emits findings on the path detector incidents already take: a `loop_signals` row (`daemon_detect_repo_config_exec` / `daemon_detect_agent_config_tamper`), `incident_alerts` delivery, and the heartbeat fold. The scan is cached on the mtime and size of exactly the files it reads (`.git/config`, `.vscode/tasks.json`, the `_AGENT_HOOK_FILES` entries) and nothing else, so an unchanged repo is never re-read and a repo poisoned *after* it was first seen clean is re-scanned on the next tick. Cache bounded at 500 directories, oldest evicted. `CLAWMETRY_REPO_SCAN=0` turns it off.
- **Honest about what it buys.** For GitSpawn the payload has usually already run by the time a session exists, so this is not prevention and the incident copy does not claim to be. It tells the operator the machine may be compromised, which today they never learn at all, and on runtimes with a pre-tool gate the finding can hold the next action. `clawmetry scan-repo`, run before an agent opens the folder, stays the preventive path.
- **Deliberately not wired to enforcement.** Workspace findings do not enter the policy pass. A policy with `trigger_kind: ""` matches any kind, so feeding them in today would let a standing "pause anything critical" rule pause a session because of a property of its folder, with no way to write "except that". Findings carry `spend_at_risk_usd: 0.0` with basis `unknown`, never an invented figure, because a queue sorted by a fabricated dollar number is worse than one that is not sorted.
- **A cwd bug underneath it.** `_detector_session_facts` read only `metadata` and ignored the `sessions.cwd` **column**, which is what `query_repo_activity` filters on and `process_control` promotes to find a pid. On the machine this was found on that column is the only cwd source for all 41 sessions that have one, so the facts every detector prices path escapes against carried `""` for every cursor, opencode, goose, pi and qwen_code session.
- **Verified on live data, not fixtures:** a real `opencode` run in a repo whose `.git/config` sets `core.fsmonitor` to an inert marker command landed in DuckDB with that cwd; feeding that real session row plus its 3 real events through `_emit_detector_incidents` emits exactly one incident, `daemon_detect_repo_config_exec` at critical, with the config line in evidence. Cost measured rather than asserted: 50 repos cold, 6.7 ms; 200 sessions spread over those 50 repos, warm, 8.1 ms total (0.04 ms per session). 14 guards in `tests/test_repo_scan_daemon_wiring.py`, **12 proven red** against `origin/main`; the file is named in `ci.yml`'s MOAT list because this repo runs explicit file lists. `scripts/redteam/audit.py` still reports 9/9. Coverage limit recorded rather than papered over: `claude_code`, `openclaw` and `codex` do not populate `sessions.cwd`, so the scan is inert for them until they do.

### Fixed: OTLP prompt-cache tokens read as zero under the current GenAI semantic convention (2026-09-08)
- **Why:** the OTel GenAI semantic conventions spell the cache counters with a dot before the noun — `gen_ai.usage.cache_read.input_tokens` — and that is what an exporter emits the moment it opts in with `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`, which is exactly what the OTel migration guidance (and every competitor's integration doc) tells people to set. `dashboard.py` matched only the underscore spelling, and neither dotted name appeared anywhere in the repo. So those spans reported **zero** cached tokens.
- **What it cost, concretely:** cache counters are not stored as a column — they feed `estimate_event_cost_usd`, so reading zero means the cache-aware cost path has nothing to be aware of. On a single span with 1,240 input / 312 output / 9,000 cache-read tokens the derived cost came out **$0.0084 instead of $0.0111**: the 9,000 cached tokens priced as free rather than at the cache-read rate. On a long agent session cache reads are usually the *majority* of input tokens, so this is not a rounding difference, and it silently affects the newest sources hardest — the ones on the current convention.
- **What:** both dotted names added as additional aliases ahead of the existing ones. `_pick` returns the first non-`None`, so a span carrying both spellings is counted once and nothing double-counts. Fixed in the live mapper and in the `DEAD COPY` above it, so a future reader does not take the shadowed one as the pattern.
- **Verified by mutation, not by assertion alone.** 9 guards in `tests/test_genai_cache_semconv.py`, built on real protobuf spans through `_process_otlp_traces` and asserting on the **derived cost** — the thing a user would notice — rather than on an internal variable. Reverting the fix turns 3 of them red with the real numbers in the failure message (`assert 0.0111 == 0.0084`); restoring it turns them green. Registered in `ci.yml`, since CI runs explicit file lists and an unregistered file never runs.

The CLI installers have no bundle stamp to floor against, so they verify the result functionally instead: after pip reports success they `import clawmetry, duckdb, cryptography` and fail with actionable guidance if it is missing, since a release old enough to have been backtracked to does not carry today's dependency set. ### Fixed: the pid-reuse guard refused every Guard action because it compared the wrong timestamp (2026-09-05)
- **Why:** with the session-id namespace fixed (#5529), Pause on a real Claude Code session stopped answering "session not found" and started answering `pid_guard_refused:start_mismatch(recorded=epoch:1788471021, live=lstart:Thu Sep 3 23:30:14 2026)`. Both numbers were right; they measure different events. `claude_code_session_map` recorded `startedAt` - the moment claude_code *wrote its session record* - and the pid-reuse guard compares its recorded value against the *process's* start time from `ps -o lstart=`. On the machine where this was found the two are 7 seconds apart, so the guard refused every pause, stop and kill on every session, having correctly detected a mismatch between a process start and something that was never a process start. The preference was deliberate and the comment explains it: `procStart` is a ctime string claude_code renders in UTC, which does not compare textually against local-time `ps` output, so `startedAt` looked like the unambiguous choice. But that comparison problem was already solved - `_start_tokens_equivalent` normalises both sides to an instant and reports `verified_tz_normalized` - while measuring the wrong event had no remedy anywhere downstream.
- **What:** the map records `procStart`, the process's own start time, and exposes `startedAt` separately as `started_at` for callers that want to know when the session began. Where no usable `procStart` exists the recorded start is `None`, so `verify_pid` degrades to an honest liveness check; falling back to `startedAt` would restore a value guaranteed to mismatch, which refuses every action.
- **Verified:** the test that asserted the old preference is replaced by one asserting the corrected contract, plus an end-to-end test that spawns a real process, renders its start the way claude_code does (a UTC ctime string), and requires the guard to pass; both are red against the unfixed file. Against the founder's live node, the guard went from refusing every session to passing 10 of 11 - the eleventh has no session record at all and is correctly refused.
